# 返工中的保留清单

收到返工/恢复 briefing 时，先读它绑定的当前合同、完整 feedback 及证据。
把本次工作写成“修复项 + 保留项 + 复验范围”，记录在现有实现总结/验证报告中。
不另造任务合同，不原地修改冻结需求，不把旧绿当成本轮通过。

| 项 | 内容 |
| --- | --- |
| 修复 | 失败 AC、可达触发、根因、受影响 owner/path、最小变更 |
| 保留 | 必须仍成立的具名行为、来源 AC、原测试/证据引用及版本 |
| 复验 | 当前目标版本、修复探针、可能受影响的保留行为、命令或已获准复用的 receipt |

保留清单从完整 requirement_results、原验收与实际实现取得；不能只读取
failed_acceptance_ids。既有 rework-feedback.v1 的 summary、required_actions、
requirement_results 与 evidence_refs 已能承载这些信息，按本次 wrapper 允许字段填写。
长正文绑定允许的 sidecar；不把运行态文件当普通文档直接写入。

例如事务失败需要回滚时，同时保留“同键同请求返回原结果”和“权限拒绝零副作用”。
修复不能通过移除幂等、放宽权限或删除失败断言实现。若只修一个事务 owner，
不要重写无关叶子；若根因是共享契约/计划错误，提交受影响范围和受控 replan 建议。

旧证据不符合本次 tree/revision/generation，或变化跨越其影响边界时，在当前候选
重新验证；符合当前复用策略时引用有效 receipt。由已有 Kernel/验收门禁检查绑定。
缺少旧证据记为未知，不能写“原来通过所以无需验证”。

保留每轮避免的错误状态、已验证正确的部分和剩余失败。触及既有预算/重试上限时
交回受控恢复路径；不重置次数，不整体回滚其他任务的成果。Verify 逐项核对保留清单，
Thin Judge 只消费被接纳的最终证据。
