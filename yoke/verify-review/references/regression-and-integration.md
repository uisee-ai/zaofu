# 用具体回归说明缺口，并验证组合后的产品

先读来源/AC、变更及真实消费者，再审相关测试的 setup 和断言。
覆盖率、文件名、测试数量或某种测试形式不能单独证明充分或不充分。
事件、外部调用本身是公共合同的场景，可以直接断言相应事件/调用结果。

## 缺口必须可复现、可返工

在既有 `gap_findings` 中说明：来源/AC、受影响入口与 owner、最小现实回归、读过的
测试及漏检原因、建议增加的行为断言、验证层级和证据引用。沿当前报告 schema
填写，不创建第二份 verdict。无缺口可报告无阻断发现，不凑数量。

例如：请求冲突时 API 错误接受并写入，但现有测试只检查响应有 `id`，未断言
规定的冲突状态与数据库无副作用。新增断言应使该回归失败；只验证 mock 被调用
或返回体存在不会补齐这一缺口。

需要证明测试敏感性时，在隔离副本中注入最小回归，记录补强前后结果并撤销回归。
清楚标记这是故障注入，不能冒充当前产品发现；不得为了 finding 修改真实候选。
环境失败、测试本身错误、需求歧义、实现错误与集成冲突分开报告，按已有路由返工。

## Task Verify 与 Candidate Verify

Task Verify 只要求本片及已成立前置能够产生的结果；未来生产者明确的 mandatory
验收继续保留，不能将未到时点的行为判绿或要求当前片伪造实现。

Candidate Verify 在最终集成树上核对：

1. Epic/原始 Goal 的全部 mandatory 条款都有当前证据，延期问题仍可见且已按需要解决。
2. 真实入口贯通：生产者输出与消费者输入兼容，API/事件/数据模型不是各自 mock 成功。
3. 共享事务、权限、错误后态、幂等和必要回归；覆盖跨任务最小用户旅程。
4. 测试、receipt 与最终 candidate 的 tree/revision/generation 相符，局部旧绿不替代集成绿。

测试失败定位到行为、任务及最小返工范围；计划/契约错误提出受控 replan，不能由
Verify 私改 Task Map。证据缺失保持未通过，不把“所有子任务 done”当目标完成。

Thin Judge 消费被接纳、同目标版本的覆盖与验证证据判断 Goal closure；不能接管
上述探索、修代码或补跑产品验证。Kernel 仍负责证据检查、返工路由和最终状态迁移。
