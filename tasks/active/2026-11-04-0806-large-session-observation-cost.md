# 大型 provider 会话读取的控制面开销

> 状态: proposed

LS 实测 Codex 会话已约 218 MiB，控制面重载后仍持续占用约 90% CPU、3 GiB RSS，进程读取计数数分钟内累计数 GiB。尚未用进程采样确认唯一热点；现有 Codex usage 读取对全文件 read_text + splitlines，交付观察也全量收集会话输出，需要分别基准和识别调用链。

1. 以脱敏合成大型会话和现有调用链复现 CPU、内存与重复读取 -> verify: 提供基线及正确性对照，不读取或提交真实会话内容。
2. 针对已确认热点实施有界、按需或增量读取 -> verify: 多条用量、metadata、追加、截断、替换、部分行和异常场景与原语义一致；保持权限、摘要绑定及未知状态，不把历史出现等同模型当前记忆。
3. 运行受影响调用方、事件和恢复闭包 -> verify: 回归、sentinel 与 mock 流通过；仅重载控制面并保留在途 provider，记录现场 CPU/RSS 和吞吐变化。

## 已复现与第一阶段

真实会话只读测量：228,520,217 字节的 Codex transcript 上，旧
`read_latest_usage` 单次 1.66 秒、峰值 1,059,980 KiB；逐行扫描版本在
228,647,196 字节时单次 1.64 秒、峰值 22,468 KiB。两次会话内容随运行
增长，不能视为严格配对 benchmark；结果只证明单次用量读取内存下降，不能证明
控制面整体 CPU 降低。继续读全文件以保持最新 metadata / usage 语义，不引入
基于不可靠追加假设的缓存。真实运行中尚未通过进程采样确认全部热点，交付输出
单次扫描 2.18 秒、151,552 KiB，后续需进一步验证实际调用频率。现场部署验证
和其余 CPU 瓶颈仍待完成。

## 控制面堆栈与范围计算

08:12–08:14 UTC 对控制面主线程进行 45 次定时调用栈采样（仅函数路径，
无请求正文），采样结束自动停止。启动后 33 次样本中，14 次位于
`run_scope.run_aliases`，调用来自 Run Manager、Supervisor、终态及恢复检查；
也观察到 automation projection 重读历史归档。LS 日期归档总计约 742 MiB。
这是一小段堆栈采样，不是全量 CPU 火焰图，不能据此推定唯一瓶颈。

终态判定原来对同一批事件构建运行身份映射 2–3 次；本次在同一调用中传递
已计算映射，外部每次调用仍重算，未引入跨调用缓存或更改跨 Run 隔离。4 万条
合成事件的局部基准：旧 0.568 秒，新 0.201 秒，终态一致。需继续做完整
回归与现场 CPU 对照；其他范围计算和归档重读仍未消除。

08:17 部署终态范围优化后，现场控制面仍约占一个 CPU 核心、RSS 约 3.1 GiB；
因此不能判定性能问题已解决。进一步复现 Run Manager 的单个 goal projection
对同一事件重复生成三次身份映射；改为每个 projection 内共享完整映射，跨调用
仍重算。24 组单 Run、多 Run、别名与未绑定事件对照的投影值一致；40,001 条
合成事件基准从 0.575 秒降至 0.268 秒（单次，非现场吞吐承诺）。相关 322 项、
sentinel 53 项、mock flow 10 项通过；现场部署与整体 CPU 对照待完成。

08:21 目标投影优化部署后控制面仍约 91% CPU、3.1 GiB RSS，不能宣布整体解决。
以 LS 只读快照做单次身份映射对照：108,674 条事件、79 个 alias，优化前后
结果完全相同，耗时 0.232 秒与 0.184 秒。另有 1,000 组合成随机历史映射
相同。无显式身份且无可用既有 correlation / anchor 的事件只绕过不必要的
构造，全部事件仍参与处理，不作时间截断或跨次缓存。相关闭包及现场验证待完成。
