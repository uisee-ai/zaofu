## 1. 问题与目标

用户通过 Kanban Agent 建群讨论需求，原本还想继续补充，系统却可能在最后一道澄清题
回答后自动开始综合。自动消息显示为 operator，使用户难以分清哪些是自己的意图、
哪些是系统调度。讨论阶段、事实核验、共识与发布校验又共同影响综合入口，用户需要
猜测“现在能不能生成 PRD”“停止生成会不会改变整个群的状态”。

新增 `libre_discuss`，提供一个可以持续交流的需求讨论群：

- 用户决定何时开始说话、请谁参与、何时形成 PRD。
- 主持人负责默认接话、有限的成员接力、问题整理与进度说明。
- 系统保留调度、幂等、身份、来源和版本校验，但不以整群讨论阶段限制交流。
- PRD 生成、评估、确认、创建父 Task 和启动 Plan Workflow 是可区分的操作。

产品显示名为“自由讨论”；内部模式值统一为 `libre_discuss`。
`libre-discuss` 用于文档名称，不作为第二套模式实现。

### 1.1 范围

本设计覆盖：Kanban 建群、成员回复、主持人调度、问题题卡、手动 PRD 综合、生成进度、
异常恢复及新旧模式兼容。

保留现有一键创建 profile、邀请成员、角色配置、附件和题卡能力，复用既有 PRD
正文/结构化合同、预览、评估、确认及 Task/Workflow 交接链路。

本次不重写 Kanban Agent 的全部能力，不替换开发工作流，不建立新的 PRD 格式，
不把现有 Channel 批量迁移成新模式，也不默认开启持续无人值守圆桌。

## 2. 已确认的产品决定

以下条目是本设计的输入约束，实施时不能改成相反的默认行为。

| 编号 | 决定 |
| --- | --- |
| D-01 | 新建 Channel 默认 `libre_discuss`；已有 Channel 和旧模式保留。 |
| D-02 | Kanban 可以创建 Channel，但不携带讨论 seed，不自动发起讨论。 |
| D-03 | 保留一键创建 profile、添加与邀请角色；主持人仍可提出角色缺口与邀请建议。 |
| D-04 | 用户可 `@all` 或点名单个成员；主动发送未带提及的消息时，由主持人默认接话。 |
| D-05 | `@all` 可由主持人组织一次必要接力；`@单人` 只由该成员回答。 |
| D-06 | 同轮至少两个 Agent 实际回复，且识别到至少两个问题时，先去重，再呈现题卡；不得因话题相近删除独立问题。 |
| D-07 | 去重失败时，显示原始题卡并标明“未去重”；用户可回答和继续聊天。 |
| D-08 | 用户回答问题不会自动触发综合；生成 PRD 由用户主动点击。 |
| D-09 | 综合入口始终开放，不依赖讨论阶段或成员共识。 |
| D-10 | 按点击生成时固定的材料生成；后续回复与用户补充留给下一版，并明确提示。 |
| D-11 | 生成后沿用评估、确认和父 Task/Plan Workflow 的既有受控流程。 |
| D-12 | 自动组织以主持人身份呈现，不能伪装为 operator 的主动发言或用户授权。 |

### 2.1 工程默认值

以下是为使方案可实施而选定的默认值，不是对竞品现有能力的描述：

- 沿用 Channel 的 `leader_member_id` 作为主持人；PRD 模板通常为 `product_pm`。
- 新模式的 `default_responder_id` 默认指向主持人；综合者沿用配置，通常为
  `synthesizer`。主持人与综合者可以是同一成员，但两类调用的职责仍要区分。
- 未带提及的消息按“发给主持人”的单人请求处理，不借此自动扩展参与者。
- 每次 `@all` 最多增加一个接力批次；每个被选成员在该批次最多回复一次。
- PRD 首次生成默认一份在执行；重复点击打开当前请求进度，不暗中创建多份或替换材料。
- 不新增“生成后自动全文评估”策略，沿用当前显式评估入口；评估不决定能否继续聊天。

## 3. 用户体验与责任边界

### 3.1 安静建群

Kanban 建群方案展示群名、模式、主持人、成员、profile 与综合者。确认方案后只执行
创建及成员配置，用户随后进入空的聊天空间。

建群指令、Kanban 内部路由对话及原始建群请求只作为创建动作的审计来源，不复制成群内
第一条业务消息，不自动变成 PRD 的需求来源。项目 Brief 可作为用户选择的材料，不以
“去掉 seed”为名把整个 Brief 隐式换一种形式注入首轮讨论。

`zf start` 或 Web 页面刷新只启动/恢复运行能力，不应为安静的新群补发开场讨论。
已持久化且获得授权的具体请求可以恢复执行，恢复不产生新的用户意图。

### 3.2 发言与有限接力

| 用户动作 | 首轮响应者 | 自动组织边界 |
| --- | --- | --- |
| 普通消息，无提及 | 主持人 | 主持人回答或提出建议；不自动拉其他成员。 |
| 点名单个成员 | 被点名成员 | 不因主持人或该成员在文本里提到别人而追加调用。 |
| `@all` | 本次可发言的有效成员集合 | 首轮结束后，主持人可安排一个必要接力批次。 |
| 回答题卡 | 更新相应问题的答案 | 不等同 `@all`，不自动开启新一轮讨论或 PRD 综合。 |
| 点击生成 PRD | 配置的综合者 | 创建独立产物工作；不重新启动讨论阶段。 |

`@all` 的成员集合在请求受理时固定，排除观察者、已移除、禁用或不具备发言权限的成员。
主持人和综合者若属于可发言成员，也可提供本轮贡献；随后承担的组织或去重调用不算
新的首轮贡献。成员变更不追溯扩大已开始的请求。

主持人接力用于补齐具体跨专业问题、事实核验或明显冲突，不用于自动延长聊天、反复
要求全员签收或追求抽象共识。接力必须说明目标，不能二次广播，也不能让接力回复继续
开启第三批调用。无接力需要时，不强制增加一条长总结或“已收到”消息。

用户发送新消息后，尚未发出的旧轮自动接力停止追加。已经开始的工作不被假装取消；
其结果仍绑定原轮，用户能区分旧轮回复与新轮回复。开始打字本身不向后台伪造取消。

### 3.3 主持人身份与用户权限

需要分开保存并呈现三件事：谁授权、谁提出调度、谁执行。

| 场景 | 授权与意图来源 | 群内呈现 | 实际执行 |
| --- | --- | --- | --- |
| 用户点名 | 用户原消息 | 用户消息及真实成员回复 | Runtime 分派目标成员 |
| 主持人必要接力 | 用户的 `@all` 范围 + 主持人结构化安排 | 主持人姓名及安排原因 | Runtime 校验后分派 |
| 按配置自动去重 | 用户已选择的本模式整理策略 | “主持人 · 问题整理”，说明正在归并 | Runtime 调用配置的整理者 |
| 用户请求 PRD | 用户的生成动作 | 用户请求记录 + 综合者进度/结果 | Runtime 调用综合者并发布产物 |
| 格式修复 | 已受理的同一产物请求 | 本次产物的修复进度 | Runtime 的有限重试 |

不能只把现有 `member_id="operator"` 改成主持人，再继续使用 `role="user"`
绕过路由。主持人发言属于 Agent/协调行为，不能获得用户权限。

固定整理策略由 Runtime 执行时，应标明自动整理来源和主持人归属，不虚构主持人已经
阅读材料或作出某项语义判断。必要接力的成员选择与理由由主持人提供结构化意图，
Runtime 只校验范围、身份、次数、版本、预算和可执行性。

### 3.4 拉取新角色

保留两条现有入口：用户从已有 profile 邀请成员，或一键创建新 profile 后加入；主持人
在正常回复中发现职责缺口时，也可提出有理由的邀请建议，沿用用户批准的受控入群流程。
提议和已入群必须区分，不能把同一待决邀请反复发送。

新模式中，入群本身不自动要求新成员发言、补交贡献、签收全部历史或开启新一轮。
用户之后可直接点名新成员，或在下一次 `@all` 中让其参与；其回复按权限取得必要历史
上下文，不要求用户重新抄写整个讨论。原轮已固定的响应成员集合不因入群被静默扩大。
邀请待处理、新成员尚未回复，均不阻塞聊天或用户请求 PRD。

### 3.5 主持人主动消息的范围

主持人的发言和调度限于已经发生的用户交互，不因群创建、页面打开、空闲计时或答完题
自行开启话题：

| 触发 | 可以发送的内容 | 边界 |
| --- | --- | --- |
| 用户普通发言未点名，或明确点名主持人 | 正常回复、必要澄清、简短归纳及角色缺口建议 | 不因此调用其他成员。 |
| 用户 `@all` 后需要补齐具体缺口 | 一次有理由的定向接力，例如请架构师核对事实、请产品经理解释冲突 | 不扩展为连续圆桌；新角色先走邀请批准。 |
| 本轮达到问题整理阈值 | 整理进度、归并题卡；失败时原题回退说明 | 不声称问题已答，不附带启动综合。 |
| 已授权的回复、邀请或产物工作产生重要结果 | 简短的完成、失败或待处理说明 | 能用局部进度/通知表达时不额外调用模型，也不强制发聊天长总结。 |

邀请建议可附在既有回复或上述接力安排里，不为检查“是否缺人”再启动后台循环。
答题完成后不自动长总结、催促确认、全员评审或生成 PRD；用户可继续补充或主动生成。
用户主动请求总结或 PRD 后，对应工作可以提供结果和有限的格式修复进度，权限不由
主持人自行扩大。

## 4. 无整群阶段门槛，保留局部执行进度

`libre_discuss` 不运行旧模式的
`phase1_blind → phase2_relay → phase3_synthesis` 自动讨论生命周期。
新模式不依赖 `questions_frozen`、`ledger_converged`、全员签收或
`Owner decision blocks consensus` 来允许聊天及发起 PRD 请求。

系统仍需保存以下局部事实：

| 对象 | 需要记录的进度 | 不能产生的效果 |
| --- | --- | --- |
| 一次成员回复 | 排队、执行、完成、失败、取消、结果未知 | 某成员失败不能封闭整个群。 |
| 一轮问题整理 | 收集、去重、已呈现、失败回退 | 去重失败不能禁止聊天或生成草稿。 |
| 一个问题 | 待答、已答、待核实及来源 | 未决问题不能被伪造为已解决。 |
| 一次 PRD 生成 | 已受理、排队、生成、校验/修复、成功、失败、取消 | 失败不能清空对话或覆盖已存在的正式版本。 |
| 一个 PRD 版本 | 草稿、评估发现、确认与执行资格 | 生成或签收不能自动授予开发权限。 |

前端不向新模式提供旧讨论流程的 Start/Restart/Drain/Consensus 等阶段按钮。
成员、聊天、问题题卡、附件与 PRD/评估/Task/Workflow 入口继续存在；PRD 和开发进度
放在相应产物或执行区域，不显示为用户必须依次解锁的整群讨论步骤。

## 5. 一轮讨论与问题呈现

### 5.1 轮次边界

“一轮”是由一条用户原消息发起的一组回复，不是一个持续到全员达成共识的会话：

1. 固定原消息、目标成员和材料引用。
2. 收集目标成员的最终回复。若为 `@all`，还可以包含主持人批准的一个接力批次。
3. 目标回复完成，或按既有回复期限进入失败/取消等终态后，结束本轮收集。
4. 按本轮实际回复和识别问题决定是否去重，随后一次性呈现本批题卡。

轮次标识、父消息引用属于内部关联字段，不要求用户理解或写进聊天 prompt。
并发的新用户消息拥有自己的关联，不能把相邻时间的两轮问题混成一轮。

模型流式中间 JSON、Provider 重试、重复完成回调及主持人的固定进度说明不增加 Agent
回复计数。相同成员一轮内有多次有效回复也只算一个 Agent；不要求每个回复者都提问。
问题数按系统最终识别到的有效问题计，普通聊天中的随口疑问不靠关键词自动变成题卡。

### 5.2 聚合与去重

阈值为：`不同已回复 Agent 数 >= 2` 且 `有效候选问题数 >= 2`。

| 情况 | 呈现方式 |
| --- | --- |
| 没有识别到问题 | 不创建题卡。 |
| 未达到阈值 | 本轮收集结束后直接显示原始有效题卡。 |
| 达到阈值 | 先请求整理者比较完整候选批次；归并结果通过机械校验后显示题卡。 |
| 去重失败、取消或超过既有执行期限 | 显示原始有效题卡，标明“未去重”，不继续隐藏等待。 |

候选问题在去重前可以进入事件记录与暂存投影，但不得提前进入 Web/Inbox 等面向用户的
可答队列。去重期可以显示简短的“正在整理问题”，不能同时提示用户立即回答尚不可见的题。

去重由整理 Agent 判断语义。保留问题来源、原题到归并题的映射、选项及推荐答案的依据；
不同承诺、真实分歧和互斥选择不能为降低题数而静默合并。现有 Ask User Question
题卡的显示与回答方式保持一致。

#### 5.2.1 去重不得丢失独立问题

仅把“请求同一项决定”的等价提问合并。整理者必须比较决策对象、适用场景、约束、
选项含义及答案的适用范围；对保留题的一个完整回答，应无需新增判断就能解决其余题。
主题相似、关键词相同、推荐答案相同或某项决定会影响另一项，都不等于重复。

例如，“刷新后是否保留数据”和“关闭浏览器重开是否保留数据”涉及不同场景；
“是否在本机保存”和“是否跨设备同步”涉及不同能力，不能只留下其中一题。
如果一题包含 A、B 两项选择，另一题只问 A，也不能整体删除前者而丢掉 B。
首版优先保留原题，不为缩短队列改写成含糊的复合题；不能确定等价时保留各题。

每条原始有效问题都必须有去向：原样保留，或映射到明确的等价保留题，并提供合并理由。
原题、选项和来源完整保存，不能因候选没有被列入合并计划就消失。转交成员核实的事实
问题另行保留及显示处理去向，不算已解答或已删除。

Runtime 对来源批次覆盖、唯一映射、有效题目身份、版本及环进行机械校验；覆盖缺失或
无效时不应用该批结果，按失败策略回退原题。这只能防止遗漏和关联错误，不能证明
语义等价。语义判定规则放在整理者的 Skill/提示中，以真实合并样本和反例验证；验收
同时检查独立决策、不同选项与少数意见是否保留，不能用题数减少或 JSON 合格替代。

### 5.3 回答竞态与失败回退

本轮候选批次必须有不可变的来源绑定和摘要，整理结果只可应用到它对应的那一代候选。
一次发布必须幂等，不能因刷新、重放或重复回调出现两套可答题。

失败回退后，本批原始题卡已经成为用户可答对象；迟到的成功结果不再自动改写该批。
用户已答题保持原身份和答案。重试整理只能显式处理仍未回答的问题或新的批次，不能
把已回答问题悄悄移走、合并后丢失答案，或改变题卡的选项含义。

事实核验仍归负责成员，产品取舍仍归用户。技术事实没有完成核验时，应以待核实事项
进入讨论及 PRD 草稿，不转换成“用户必须回答”的伪问题，更不锁住综合入口。

## 6. 用户主动生成 PRD

### 6.1 入口与材料

新模式始终保留“生成 PRD”入口。用户可以选择当前 Channel 内容及自己提供的其他材料，
包括显式选入的项目 Brief、附件、已有 Markdown 或补充说明。材料入口复用现有能力，
不要求用户填写内部路径、事件编号或机器合同字段。

未决问题、没有全员签收、没有完成去重、只聊过一个成员、甚至尚无 Agent 回复，都不能
成为隐藏的整群综合门槛。材料不足时可先补充材料，或形成忠实标明缺口的草稿；不能
编造需求填空。空群且未提供任何材料时，在入口内说明需要添加材料，不能只给灰色按钮。

缺少身份权限、模型未配置、Runtime 离线或目标成员不可用，是具体动作的技术前置条件。
应展示原因和可继续的操作，不使用“讨论未收敛”代替技术错误，也不承诺离线仍能执行。

### 6.2 点击时固定输入

服务端受理生成动作时，原子固定一份输入快照，并回执材料范围与截止时间：

- 截止点前已入库的 Channel 原消息、完成回复、问题及答案。
- 用户选入的其他材料及其确定版本。
- 已确认的产品决定、仍未解决的问题、风险与待核实事实。
- 原材料的引用与 digest，以及本次请求的授权来源。

点击后才完成的 Agent 回复、之后的题卡答案和后续用户补充，不进入本次快照。
尚未发送或未确认保存的输入不能假装已纳入。界面提示：
“本次采用截至……的内容；后续补充可用于下一版。”

快照不以综合者实际开始工作的时间重新取最新内容。即使请求排队、进程恢复或发生自动
格式修复，也沿用同一份产品材料；错误诊断可以补入修复上下文，但不是新的产品需求。

生成期间普通聊天继续可用。同一 Provider/session 的串行要求可以造成特定成员排队，
应说明“该成员正在执行另一项工作”，不能因此锁住其他成员或整个输入框。

### 6.3 请求、版本与取消

一次点击通过既有受控动作提交，生成持久化、幂等的请求。重复提交同一动作不能重复
计费或生成多个版本；已有请求执行中再次点击时，打开本次进度与可用操作。

默认同一 Channel 一次执行一份 PRD 生成。新一版由用户在本次结束后显式发起，不因
收到新消息自动排队生成。用户可停止当前产物工作；停止不关闭 Channel、不删除问题、
不改变旧正式版本，也不等同放弃后续讨论。

失败后的“重试本次”复用原快照；“按最新内容生成新版”必须是不同的显式请求。
终态之后迟到的旧回复不能发布到新请求或覆盖新版本，结果未知的交付沿用既有核查机制，
不能仅因超时就盲目重复执行。

### 6.4 草稿、发布与质量

新模式复用现有 PRD 正文、来源、摘要、结构化覆盖、readiness 与版本合同，不另建一套
“自由讨论专用 PRD”。有未决产品事项的稿件必须标成草稿并列出缺口，不能伪造已答来源、
评估通过、独立评审完成或允许实施。

生成可读候选稿、通过机械发布校验、通过语义评估、用户确认、允许开发是不同结果：

- 未通过发布校验的候选内容可以供用户查看，但不能冒充正式 PRD 或用于创建父 Task。
- 格式与引用修复保留有限次数、清楚显示进度，不因为换了模式就关闭机械校验。
- 新版通过发布校验后，才原子成为可预览的正式草稿；旧版本仍可追溯。
- 全文评估和必要的独立评审绑定具体版本；失败发现以可读正文呈现，并可继续群内讨论。
- 本模式不默认触发旧多视角的全员共识循环、自动返工综合或 `next_round.continue`。
- 用户明确“请按刚才讨论修改 PRD”可以表达修订意图，但具体产物生成仍通过可见的
  受控请求执行，不允许 Agent 在后台自行替用户点击综合。

### 6.5 后续交接

沿用既有版本、Owner、评估、风险确认及执行授权校验。评估未通过或必要缺口未关闭，
可影响当前 PRD 的开发资格，不影响继续聊天、请求草稿和修订。

通过适用评估并完成必要确认后，用户可创建父 Task，再点击 Plan Workflow 开始
既有 PRD Workflow。主持人总结、成员签收、生成成功、评估完成都不自动创建任务或
启动开发。旧版评估和确认不能替代新版的相应判断。

## 7. Runtime 与数据设计

### 7.1 复用边界

继续使用 `EventWriter` / `EventLog`、受控动作、当前投影、sidecar、不可变来源引用、
请求幂等及 Provider 执行所有权。Web 不直接写 canonical state，Agent 不直接修改
问题台账、PRD 正式版本、Task 或 Workflow。

语义判断归主持人/整理者及对应 Skill：选谁接力、哪些问题重复、需求有何缺口。
Runtime 校验身份、消息因果、模式、轮次范围、接力次数、结构、版本和证据绑定。

### 7.2 最小关联信息

以下是逻辑上必须保留的信息，不要求为每项建立独立存储或新的全局状态机。
应优先复用现有事件与 refs；确需新增事件/字段时一并登记 schema、投影和测试。

| 对象 | 必须能重放得到的信息 |
| --- | --- |
| 讨论轮次 | 根用户消息、已固定目标、主持人、初始/接力批次、最终回复归属。 |
| 协调请求 | 人类授权根、主持人意图或固定策略、目标成员、原因、模式与范围。 |
| 问题批次 | 来源回复、候选摘要、去重代次、成功或回退、已发布题卡身份。 |
| 产物请求 | 用户动作、快照引用及摘要、综合者、当前执行/终态、发布版本。 |
| 展示身份 | 用户、真实成员、主持人自动整理、Runtime进度各自的来源。 |

协调请求必须走专门的可信控制路径，再复用现有成员回复请求/队列。不能通过任意群消息
自称主持人获得调度权，不能把 Agent 的 `role=user` 当成授权，也不能把普通文本中的
`@` 无条件升级为转发动作。

请求中应保留实际 Runtime actor、发起者、原用户授权与调度者；对外显示友好的角色名。
后台机械整理的调度归属与“主持人模型亲自作出决定”需要可区分。

### 7.3 创建与模式分流

新建默认值在创建边界显式确定，不通过修改全局未知模式回退来误迁移历史数据。
新增模式需贯通 API、CLI、模板、Kanban Plan、前端枚举、验证器与投影，不能只增加一个
下拉选项后被后端默默归一成 `conversation`。

`libre_discuss` 的建群 Plan 使用现有“仅创建模板群”能力，不调用创建并启动讨论。
`discussion_seed` 在此模式下为空或省略；原创建意图只作审计绑定。若收到显式要求
create-and-start 的矛盾请求，应返回可理解的模式不匹配，不静默开始第一轮。

旧模式继续走各自原有路径。所有自动推进、去重恢复、自动综合、评审返工和下一轮反应器
都必须以模式/请求类型判断归属，不能仅因同名事件出现就误推进新模式。

### 7.4 资源、恢复与并发

- 轮次收集、候选批次与快照使用已有投影、索引和 sidecar，避免每个流式 token
  都全量读取项目事件历史；完整语义材料按引用读取，摘要不能替代正文。
- 并发度与回复期限沿用项目现有配置；任一成员不能无限阻止问题批次结算。
- 主持人接力、去重和综合请求分别幂等，不能因多个唤醒事件重复计费。
- 重启后恢复具体未完成请求与来源，不重发建群 seed，不制造新轮。
- 取消、移除成员、迟到结果和重复回调都受当前代次及终态检查。
- 不为“给自动调用换一个署名”增加额外的模型轮次；仅需要语义安排时调用主持人。

## 8. 前端与 Kanban Agent 改动

### 8.1 Kanban Agent

建群工具合同、提示和确认卡统一表达“创建一个自由讨论群”。保留 profile 与成员配置；
创建完成只提供进入入口，不承诺已开始讨论，不把建群请求作为需求 seed。

引导用户用普通语言和角色显示名交流，不要求提供内部事件号、请求号、状态目录路径。
用户求助“为什么不能生成”时，网页应已有具体原因和当前请求入口，不能必须回到 Kanban
让 Agent 读取内部台账才能继续。

### 8.2 Channel 页面

- 页面沿用原有 Brief → Discussion → PRD → Tasks → Workflow 导航、摘要和详情抽屉，
  不再为自由讨论单独放置三按钮工具栏。导航是需求、产物与交付的只读入口，不是聊天的阶段门槛。
- 自由讨论显示为 Free discussion；已有问题保留待回答标记。PRD 生成进度按本次请求显示，
  不要求进入旧模式的 synthesis 阶段。PRD 导航始终可进入。
- 自由讨论的使用提示、整理进度和原题回退提示放在 Discussion 抽屉；Synthesize 打开材料选择，
  由用户显式提交生成，不恢复 Start/Restart/Drain 或自动推进。材料选择独立于 PRD 阅读抽屉；
  Preview 与 Source 恢复原有正文、工具栏和评估区，不在正文顶部插入下一次生成的表单。
- 显示当前主持人、成员与自由讨论模式；首次空群给静态使用提示，不调用 Agent 欢迎。
- 普通消息交给主持人；成员提及选择器、`@all`、题卡与附件沿用现有交互。
- 具体成员的排队/回复/失败与本轮整理进度就近显示，来源不显示成 operator。
- 用户答完问题后仍停留聊天，不跳入自动综合页面。
- “生成 PRD”入口不依赖讨论 attention 的 `can_synthesize`；进入后显示材料与请求状态。
- 原始题卡回退必须有“本轮去重失败，以下为原始问题”的可读提示。
- 原始 JSON、仅有 RISK/GAP 编号、内部合同错误放到详情，不能代替面向用户的正文。
- 生成失败时可查看具体原因、已有候选稿、旧版本与可用重试，不要求关闭整个 Channel。

### 8.3 投影契约

前端需要区分：频道模式、当前回复/问题批次、PRD生成请求、PRD版本及后续执行资格。
不再把新模式折叠到同一个“Discussion Ready/Blocked”布尔值。

读模型必须与受控动作一致：若显示可回答，动作不能又以隐藏的去重门禁拒绝；
若生成入口可进入，服务端不能再以旧讨论 phase/freeze/consensus 为理由拒绝新模式。
技术前置条件及产物自身并发限制仍应通过可读动作结果表达。

## 9. 兼容与上线

1. 新模式作为新增值实施，旧模式及历史别名继续可读、可运行。
2. 新建默认自由讨论；用户明确选择旧模式时，保留其既有语义与界面。
3. 已有 Channel 不自动改模式，不重写历史 operator 消息，不清空问题、签收或 PRD。
4. 首版不提供进行中的跨模式迁移；若复用现有设置入口，活跃请求期间拒绝模式切换并
   解释需先结束具体请求，不能破坏正在执行工作的来源与版本。本批不提供原地模式迁移，引导建新群。
5. 回滚前停止新建该模式并保留已创建数据；旧版本不能把未知新模式悄悄按旧自动模式运行。
   不兼容版本应拒绝执行该群的自动动作并给出说明，不能回滚成自动发 seed 或自动综合。

## 10. 验收与验证方案

以下是本设计的验收标准；已执行范围以实施记录为准。自动化优先覆盖行为与跨模块合同；
真实 Provider/浏览器端到端验证单独记录，不能用单元测试替代真实体验。

| ID | 步骤 → 验证 |
| --- | --- |
| AC-01 | Kanban创建未指定模式的新群 → 模式为自由讨论，profile/成员正常，群消息与Agent调用均为0。 |
| AC-02 | 对新空群启动/重启Runtime并刷新页面 → 不补发seed、不开始讨论。 |
| AC-03 | 用户发未@的消息 → 只由主持人先回复，无额外成员调用。 |
| AC-04 | 用户@一个非主持人成员 → 只有指定成员回复；其正文@其他成员不自动扩员。 |
| AC-05 | 用户@all → 固定有效成员集合，实际回复均绑定同一轮；主持人最多增加一个必要接力批次。 |
| AC-06 | 接力成员再次请求别人/广播 → 不产生第三批或二次全员广播，用户仍可继续说话。 |
| AC-07 | 两个Agent完成回复，只有一个提问但共两题 → 触发前置去重，合并前没有可答题卡。 |
| AC-08 | 单Agent两题、或两个Agent仅一题 → 不触发去重，本轮结束后原生题卡可答。 |
| AC-09 | 一个Agent有重复完成/格式重试/接力多条输出 → 不被算作多个Agent，重复回调不复制题卡。 |
| AC-10 | 去重成功 → 只呈现该批归并后题卡，原题映射、选项含义和来源可追溯。 |
| AC-11 | 去重失败/取消/到期 → 原始题卡标明未去重、可回答，聊天与PRD入口仍可用。 |
| AC-12 | 回退题卡已有答案后收到迟到去重结果 → 不改题、不丢答案、不改变选项含义。 |
| AC-13 | 最后一张题卡回答完成 → 不产生自动synthesis请求，不自动评审或启动下一轮。 |
| AC-14 | 两条用户消息及其回复交错到达 → 问题与回复仍归各自原轮，不跨轮凑阈值。 |
| AC-15 | @all中一个成员失败/取消，其他成员完成 → 按有效回复结算，显示局部失败，不无限等待或锁群。 |
| AC-16 | 用户发送新补充时旧轮尚有未发出的自动接力 → 不再追加旧轮接力；已执行回复保留原轮归属。 |
| AC-17 | 有未答题、待核实事实、未签收或从未完成整轮讨论时点击生成 → 入口可进入，不以旧阶段拒绝。 |
| AC-18 | 空群且无其他材料、模型缺失或Runtime离线时进入生成 → 显示具体前置条件及可用下一步，不是无原因禁用。 |
| AC-19 | 点击生成后Agent晚回复、用户补充或改答题卡 → 仍可聊天，本次稿只采用原快照，回执提示截止范围。 |
| AC-20 | 请求排队、重启或格式修复后开始生成 → 材料摘要与原快照相同，未偷换为最新上下文。 |
| AC-21 | 用户重复提交同一生成动作 → 只有一个请求；执行中再次点击可查看当前进度，不替换快照。 |
| AC-22 | 生成失败/取消时已有旧PRD → 旧版保留、聊天可用，停止不关闭Channel。 |
| AC-23 | 重试本次与按最新生成新版 → 前者保留快照，后者显式创建新请求；迟到旧结果不能覆盖新版本。 |
| AC-24 | 存在未决产品项生成正式草稿 → 原样保留未决/待核实项，不虚构用户决定或评估通过。 |
| AC-25 | 草稿候选缺结构或证据合同 → 可读候选与正式版本明确区分，未合格候选不能用于父Task。 |
| AC-26 | 主持人调用成员及自动去重 → UI身份可辨认；审计可区分原用户、主持人和Runtime，不出现伪造用户授权。 |
| AC-27 | 普通Agent冒充主持人或role=user请求调度 → 请求被拒，不能越过成员范围、次数或人类权限。 |
| AC-28 | 对具体PRD版本评估、修订、确认、创建父Task及启动Plan Workflow → 引用同一适用版本与授权，不自动执行。 |
| AC-29 | 在三种旧模式和历史Channel执行原有路径 → 不被新模式默认值、去重策略或UI分流改变。 |
| AC-30 | 查看问题、风险、失败及评估发现 → 有可读内容和下一步，不要求普通用户理解内部编号或JSON。 |
| AC-31 | 从已有profile邀请，或新建profile后拉入角色 → 均能入群；入群不自动发言，之后点名/下一轮@all可取得必要历史并正常回复。 |
| AC-32 | 主持人发现角色缺口 → 显示有理由的待批准邀请；不重复提议、不冒充已入群，待决邀请不阻塞聊天或PRD。 |
| AC-33 | 输入严格同义题及话题相近但场景、能力或选项含义不同的题 → 仅等价题合并，其余完整保留，不以推荐答案相同为由删题。 |
| AC-34 | 一题含A/B选择、另一题只问A，或存在少数意见/相互依赖的决定 → B及分歧不丢失，依赖不冒充重复。 |
| AC-35 | 合并计划遗漏原题、映射无效或转交事实核验 → 前两者不应用并回退原题；核验题有可追溯去向，不冒充已答。 |
| AC-36 | 建群、打开页面、空闲及答完题 → 不产生额外话题、长总结、催确认、自动评审或PRD；允许的接力和进度仍受原请求范围约束。 |

### 10.1 实施验证分层

- **确定性合同测试**：模式归一/创建准入、主持人权限、有界接力、候选批次、幂等、
  超时/取消/迟到回调、邀请与回复分离、原题完整覆盖、快照绑定、PRD版本及旧模式回归。
- **跨入口测试**：Kanban Plan、Web受控动作、Runtime反应器、投影与CLI对新增模式一致；
  验证新增模块确实接入真实入口，不能只测孤立函数。
- **Web组件与Playwright**：安静建群、普通发言、@单人、@all、题卡前置去重与回退、
  持续聊天、生成/重试和旧模式界面。使用隔离项目，不覆盖8001真实开发会话。
- **真实Provider最小链路**：以轻量待办idea，经Kanban建群、点名讨论、答题、继续补充、
  手动生成、预览与评估，保留失败与恢复证据；不得跳过等待或伪造PRD产物。
- **去重语义样本**：覆盖等价改述、不同适用场景、复合题与子问、选项冲突、相互依赖及
  少数意见；对照原题逐项检查决策是否保留，单独记录模型误判，不能仅以机械校验通过
  宣称误合并已经修复。
- **资源观察**：对有历史的项目核对有界读取、并发请求与长上下文处理，区分产品故障、
  Provider失败和环境限制，不以宣传视频或既有OOM消失宣称资源问题已经解决。
