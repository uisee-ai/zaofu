# 196 Inbox 人工决策中心与阅读状态

> 状态：partial — 决策投影、已读、页面与受控动作已实施；历史兼容和来源系统缺失的动作仍需后续处理。
> 日期：2026-10-30。范围：消息准入、决策处理与可见性、已读及计数、历史兼容和业务流保护。

## 1. 定位与目标

Inbox 定位为**人工决策中心**：只接收需要用户回答、审批或选择处理方式的事项。
普通运行事件、Agent 讨论、自动恢复过程和无需用户决策的结果通知不进入 Inbox。
已处理历史只保留曾经属于人工决策的事项，用于回看；不能把自动处理或普通通知
重新引入历史列表。

判断标准是用户是否需要作决定，而不是事件名称、Agent 身份或消息是否看起来重要。
需要人工处理的失败进入 Inbox 的是**决策请求**；单纯的失败结果留在原有结果和
观测页面。

成功标准：

1. 真正需要人的决策不遗漏，点击能到具体上下文并完成受控操作。
2. 阅读状态与决策状态分离；阅读后未读数减少，待处理数只随决策状态变化。
3. 用户能分辨“决定已提交”“系统已应用”和“执行失败”，不会误以为提交即恢复成功。
4. 收窄 Inbox 不删除事件、关闭审批、改变调度、绕过现有控制动作或阻断结果投递。

## 3. 准入规则与消息归属

| 信息 | Inbox | 保留位置 / 理由 |
| --- | --- | --- |
| 需要人工批准或拒绝的 Plan / 受控动作 | 是 | 必须保留可审阅的人工门禁；未启用人工审批的路线不因此新增门禁 |
| Kanban Agent 或 Channel 向用户提出的问题 | 是 | 保留原会话，提供准确的回答入口 |
| 已升级且确需用户选择的阻塞、恢复、权限或预算决策 | 是 | 展示影响、可选动作及来源；是否阻塞以原合同为准 |
| 仅供查看的 Goal / Run 完成或失败结果 | 否 | 保留在 Workflow / Run / Goal 结果、原有投递和证据链 |
| Worker 心跳、阶段进度、工具调用、自动重试、普通运行诊断 | 否 | 保留在 Workflow、Runtime、Trace 或原事件来源 |
| Agent 间讨论、普通 Channel 更新 | 否 | 保留在原 Channel / 会话；只有面向用户的问题进入 |
| 已处理、已替代、已失效的人工决策 | 历史 | 基于原始权威状态回看，不计入待处理或其未读徽标 |
| 已自动批准或自动处理、未要求人工决定的记录 | 否 | 留在原流程和审计记录中 |

同一失败可同时有运行诊断、结果和人工决策请求；只将**决策请求**投影到 Inbox。
不要把 `approval.requested` 或 `human.escalate` 整类一概过滤：它们既可能绑定真实
人工门禁，也可能承载历史兜底或旧式信号。根据已有合同、身份、来源和当前状态判断，
不以标题、错误文案、来源角色或是否有单个字段作为唯一依据。

## 4. 对现有业务流的影响

### 4.1 状态所有权

```text
Plan / Channel / Kanban / Run Manager 的原始事件与合同
                     │
                     ├─> Inbox 决策投影：谁需要决定、阅读状态
                     │
用户选择 ─> 既有受控动作 ─> EventWriter / 原业务处理器
                                      │
                                      └─> 接纳、执行、失败或恢复证据
```

Inbox 不成为新的 Task schema、审批状态机或调度器。消息移出 Inbox 只改变该视图，
不停止产生原始事件、不修改 `TaskStore` / `EventLog`、不自动批准、不解除阻塞，
也不自动执行或取消业务动作。阅读动作和决策动作都沿现有受控路径；Agent 可以
提供建议，不能代替用户批准。

Plan 审批仍由既有配置和合同决定，Kanban / Channel 回答仍在其原业务上下文生效，
人工恢复仍由既有 Run Manager / Kernel 消费。必须验证这些入口及下游结果，不以
Inbox 卡片消失证明业务完成。

### 4.2 旧式 `human.escalate`

[恢复逻辑](../../src/zf/runtime/run_continuation.py) 区分部分旧式升级通知与带人工
合同的门禁，但旧事件也可能参与恢复判断。迁移时应以原事件、决策 token、关联
Run / generation、门禁与后续权威结果核对：

- 确认需要人决定且仍有效：保留在待处理。
- 已有明确的解决、替代或失效证据：按证据进入决策历史，不改写原事件。
- 归属或状态无法判断：迁移期间保守保留可发现的“待核实”记录，不能自动批准、
  关闭或当作确定的人工决策。要记录原因并逐项对账，不能把这个兼容例外变成
  自动接收所有运行告警的长期规则。

### 4.3 结果通知和飞书兜底

从 Inbox 移出纯结果通知，不等于删除 Goal dossier、completion receipt、终态事件或
`owner.visible_message.requested`，也不应关闭原有飞书投递。现有
[Goal 交付](../../src/zf/runtime/goal_dossier_delivery.py) 和
[Run Dossier 界面](../../web/src/components/observability/RunDossierPanel.tsx) 是
核对入口；各路线的结果是否均可找到仍需验证。若外部渠道未配置或投递失败，用户
会失去一个主动提醒，必须核对原页面和投递状态的可发现性。

当前 [飞书投递](../../src/zf/runtime/owner_visible_delivery.py) 在路由缺失时创建
`approval.requested` 作为 Inbox 兜底；已有测试覆盖该行为。不能直接停发兜底而使
真正需要人工处理的原始决策消失。建议把重复的路由问题按项目和路由在设置或运行
状态中汇总，仅在配置确为需要用户决定的事项时进入 Inbox；原始人工决策应有独立、
可用的入口。当前兜底声明的配置 / 暂缓动作需要核实实际处理器，不能假定按钮可用。

## 5. 决策生命周期与可操作性

以下为用户可见的建议状态，必须由既有业务事件和实际执行结果推导，不新增第二个
canonical 状态机：

| 用户看到的状态 | 意义 | 待处理计数 |
| --- | --- | --- |
| 待处理 | 当前版本仍等待用户选择 | 计入 |
| 已提交 / 处理中 | 用户决定已接收，系统尚未给出适用的处理结果 | 不再要求重复决定；保留进度可见性 |
| 已处理 | 决策已被接纳并有相应处理结果；不等同整个 Goal 已完成 | 不计入 |
| 处理失败 | 提交或后续执行失败，展示原因；是否需要新决策由权威合同决定 | 仅仍需用户决定时计入 |
| 已替代 / 已失效 | 由原业务的明确证据证明当前决策不再适用 | 不计入 |

例如人工升级的 `acknowledged` 表示收到决定；不能单独证明 Run 已恢复。
`run.manager.human_decision.applied` 也应结合具体动作的结果字段解释，不因事件名
直接声称实际副作用成功。对明确仅要求确认的事项，按该事项自己的合同展示结果。

每条卡片应回答：**发生了什么、关联什么目标或上下文、需要用户决定什么、有什么
真实可用的动作**。按钮根据当前有效合同生成；未知动作不伪装为可批准。详情链接
应尽量携带项目、Channel / conversation、thread、question 或 request 的已有身份及
版本，并定位到原问题；目标已处理、失效或不可访问时给出清楚反馈。

历史决策不渲染可执行的批准 / 拒绝按钮。提交动作时，后端在原有权限和受控动作
路径内重新校验决策存在、仍待处理、当前版本 / generation 及允许动作；并发提交、
过期页面、重复请求和相反决定必须有一致的拒绝或幂等结果。仅隐藏按钮不能替代
后端校验。

## 6. 已读、未读与计数

### 6.1 两条独立状态轴

```text
阅读：未读 ──用户主动查看──> 已读
决策：待处理 ──用户提交──> 处理中 ──权威结果──> 已处理 / 失败
```

- 侧栏 Inbox 徽标：当前项目**仍待用户决策且未读**的事项数。
- 页面待处理数：当前项目仍需要用户作决定的事项数，已读不使其减少。
- 已提交、已处理、替代及失效的事项不计入待处理；已处理历史不计入侧栏未读徽标。
- 未读和待处理均按具体决策身份计数。展示上的分组不应把多个独立决策误算为一项，
  也不能通过阅读一条暗中阅读或处理其他决策。

例如打开一条仍待审批的消息：未读 `5 → 4`，待处理保持 `8`；审批被接收后，待处理
`8 → 7`，但页面还应显示系统处理状态。阅读不是批准、拒绝、确认恢复或删除。

### 6.2 阅读交互与版本

- 用户主动点击消息或明确打开其深链接后标记当前版本已读；页面默认选中第一条、
  轮询刷新或仅进入 Inbox 不应自动把它标为已读。
- 已读后保留卡片及待处理状态，未读标记消失；“仅看未读”模式可暂时保留正在看的
  详情，切换选择后再按筛选规则移出。
- 显示「全部标记已读」及其范围：当前项目、操作时已存在的 Inbox 待决版本。它不
  处理决策；操作期间或之后到达的新版本保持未读。
- 问题内容或可选决策发生**实质性版本变化**时重新未读；普通轮询、状态投影刷新和
  重复投递不应反复提醒。可复用原请求 revision / 事件身份或投影水位，实施时明确
  每类来源的版本依据，不能仅依赖墙上时钟或永远沿用旧 item ID 的已读标记。
- 已读动作成功后列表、页面计数和侧栏从一致投影更新；失败保留未读并提示重试。
  多窗口、刷新、项目切换、旧请求晚返回及读写并发不能覆盖较新的结果。

当前阅读事件按项目共享，没有独立的用户阅读身份。首期明确沿用这一范围，避免
暗示已支持每人独立阅读；若未来引入多用户身份，再单独设计身份和数据迁移。
旧无版本阅读事件须按可证实的事件顺序兼容，无法确定的版本保守显示未读；不能
为兼容而重写历史事件。

## 8. 去重、迁移与兼容

- 同一决策的重复投递可按稳定决策身份折叠，保留首次 / 最近时间和发生次数；标题
  相似不足以证明是同一决策。不同决策 token、版本或不同用户责任不能暗中合并。
- 聚合为视觉组时，每个独立决策仍保有身份、可见状态和独立动作；不得因点击一项
  自动批准或关闭整组。
- 首次上线先对照实际项目事件与投影，生成可复核的分类结果；不批量删除事件、
  伪造 `acknowledged` / `resolved`、修改 task / run，或把旧消息全部标已读。
- SQLite 与完整事件回退路径必须使用相同准入、版本和计数规则。投影落后或不可用
  时给出明确状态，不能把读取失败当作“没有待办”；保留既有兼容恢复路径。
- API 如调整字段或计数口径，检查现有 Web / 测试调用方及旧客户端兼容。统一从
  决策投影推导页面与徽标，避免每个界面各自统计。

## 9. 建议实施顺序

1. **决策入口与状态闭环**：核对所有人工决策来源；补齐 SQLite / 事件回退一致性；
   修复 Plan 过期 / 重复决策校验、历史按钮和提交后状态反馈。
2. **准入与业务保护**：实施人工决策准入；保留原始业务事件和受控路径；为旧式
   升级提供保守兼容，并处理飞书缺失路由的可发现性。
3. **已读与页面**：接通版本化已读、全部已读、跨页面徽标和实时刷新；简化 Inbox
   视图并准确定位原问题。
4. **历史对账与降噪**：以真实项目只读样本核对待办，按证据处理旧项和重复呈现；
   不把视觉去重当成决策状态合并。

本节保留原始实施顺序；实施状态和剩余限制见第 11 节。本文不授权批量修改历史状态。

## 10. 验收要求

每条验收均以原始状态和可观察结果为准：

1. Plan、通用人工审批、Channel 问题、Kanban 问题及人工恢复请求分别进入 Inbox →
   verify：列表、来源身份、原上下文、动作和结果与原业务合同一致。
2. 普通运行事件、纯完成 / 失败通知和自动批准记录产生 → verify：不进入人工决策
   Inbox；原事件、Workflow / Run 结果、证据和已配置投递仍保留。
3. 用户点击未读待办 → verify：该版本变已读，侧栏未读数减少，待处理数不变；刷新、
   切页和切回项目后状态一致；写入失败时保持未读并显示错误。
4. 用户全部标记已读，同时有新决策或新版本到达 → verify：只有操作时覆盖的版本
   被标记，新版本保持未读，待处理数不变。
5. Channel 问题或决策选项实质更新 → verify：旧已读不覆盖新版本；重复投递和无
   实质变化的刷新不制造新的未读。
6. 用户提交人工决定 → verify：显示已接收及后续实际结果；下游失败有明确反馈，
   没有把 `acknowledged` 或事件名当作实际恢复成功。
7. 历史 Plan、过期版本、不同窗口的并发或重复提交 → verify：前端不提供失效动作；
   后端拒绝冲突或给出幂等结果，不产生矛盾决策或重复副作用。
8. 旧式升级、重复 token 和多 generation → verify：不误隐藏仍阻塞的决策、不合并
   独立决策；状态未知时有可发现的待核实路径。
9. 缺失飞书路由或投递失败 → verify：可发现配置问题，真实人工决策仍可处理；不会
   每次失败形成大量重复待办，且不破坏原有事件与投递回执。
10. 相同事件分别走 SQLite 与完整事件回退 → verify：决策集合、状态、版本、未读和
    计数一致；投影不可用时显示未知或错误，不伪报空收件箱。
11. 浏览器从 Inbox 跳转 Channel / Kanban → verify：进入正确项目、线程和当前问题；
    已处理或失效时提供准确反馈。

后续代码变更需按影响运行对应后端投影、受控动作和前端测试；跨 API / EventLog
边界增加集成验证。浏览器端使用仓库规定的 Docker Playwright，至少覆盖真实后端
的已读与决策状态链路；mock 测试不能替代该链路。
