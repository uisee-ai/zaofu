## 3. 需求入口与各阶段的组队权

对于启用此策略的 PRD，协调责任从**已确认且绑定版本的需求**开始。OA 可以承担现有 Workflow Synthesis 的受控角色，或直接消费该次已准入的选择。入口只作一次选路。来源未确认、超出授权、能力未注册时，沿现有澄清或 Proposal 审批路径处理。Workflow 批准、Plan 人工批准和最终交付仍分别按项目策略执行。

| 阶段 | 谁选择与汇总 | 谁实际执行，怎样结束 |
|---|---|---|
| Plan | OA 按未决问题提出零个或多个辅助专家。例如 LS 身份集成需要回答开发依赖、测试身份来源和最终接入边界。每位专家有明确交付对象。 | Kernel 通过现有阶段 fanout 派发已准入的扫描或调查义务。指定一位 Planner 撰写本代正式 Plan/Task Map；OA 亲自汇总为正式稿时须承担本次 Planner 作者身份。按获准的 none/targeted/full 策略及 owner gate 完成评审。适用的独立评审由另一执行身份承担。 |
| Impl | Task Map 定义任务、契约和依赖。OA 可建议优先级、技能或人选。 | WRC 根据就绪、能力、占用、冲突与背压绑定实际 worker。记录偏好未采用的原因。普通派发自动进行。 |
| Task Verify | OA 根据 Task Map 和任务合同决定每项任务由哪类独立 Verifier 验、验哪些条款、需要什么证据。同类任务可共用一份方案。需要多名专家时，指定一位负责该任务正式结论，其余各自提交专项证据。 | 每项 Impl 交付后，WRC 将获准分工绑定到该任务的目标版本，在可用容量内立即派发。多个任务可同时 Verify，其他任务可继续 Impl。对应的独立 Verifier 签署任务结论，返工和重试归在原任务下。 |
| Candidate Verify | OA 在装配时从已注册的 Reader 容量中决定并行宽度，冻结前将全部验收项、必需用户旅程和跨任务集成检查分给具体 Reader。覆盖有缺口时由 OA 补齐分工。 | 各 Reader 在同一 Run、任务图代次和冻结候选提交上并行取证，分别签署肯定、拒绝、依赖阻塞或弃判。汇总按冻结的必需名单核对，保留分歧和仍有效的票。 |
| Judge 与交付 | OA 在授权角色范围内确定一位独立正式 Judge，列明需裁决的目标和未决分歧。必要时可让多位专项复核者并行检查证据，并指定哪些意见是主审裁决的必需输入。 | 满足既有 Judge 入口条件后，Kernel 按已准入分工派发。正式 Judge 对照目标、当期证据和必需意见签署唯一最终判词。分别展示证据就绪、Judge 派发、判词准入和实际交付回执。 |

**OA 的决定可以先于执行。** OA 可在 Task Map 准入时提交覆盖一批任务的验证分工，在阶段装配或冻结前补齐届时才能确定的范围。每次分工记录适用版本、覆盖条款、角色、必需输入及签署人。Kernel 校验权限、独立性和版本，在派发时绑定实际实例及目标。OA 选定角色不能放宽现有验收门槛，也不能改写独立判词。

例如八项任务共用一份已准入方案，前三项交付且有三个空闲 Verify 执行位时，WRC 可同时派发三项。若第四项出现方案未覆盖的跨任务依赖，只将受影响分工送回 OA。其他有效分工继续执行。断点恢复同样复用仍有效的方案与回执；只有分工缺失、绑定失效或出现需要改变策略的新证据时，才请求 OA 作出新决定。

**缺省和显式空组必须有不同含义。** 旧配置未声明选择时，沿用原 PRD profile。获准的零辅助专家方案直接交给唯一 Planner，同时保留必要来源读取、评审和授权。编译器须避免空组回退为默认双扫描，也须避免等待零名成员回执。单专家与多专家方案均受已注册能力、父级并行容量、执行权限和资源策略约束。[当前 Plan review 策略](../../../src/zf/core/config/plan_review.py) · [Candidate 宽度测试](../../../tests/test_candidate_verify_width.py)

## 4. 成员义务、派发与恢复

下面列出工作台与 runtime 需要能对账的信息。优先使用现有结构中的字段或引用；字段拼写和序列化迁移留给实现评审。

| 事实 | 至少可核对的信息 | 谁产生或更新 |
|---|---|---|
| 成员被建议、分工获准 | 需求修订、阶段及版本；阶段内稳定的成员义务标识、职责/问题、必需或可选、选人依据、完成条件、交付对象、输入范围和预期产物 | OA/合成角色提出；现有 Proposal 或受控阶段变更准入。一个职责可有多个实例，展示名或模型名不作关联键。 |
| 工作请求、实例绑定与尝试 | 适用的 Run、阶段、Task/覆盖项、operation、实际角色实例、attempt、目标版本、派发及开始时间 | Kernel/WRC 与 transport 按原入口记录。Plan 的业务 Task ID 可空；尚未派发时实例也可空。 |
| 结果、交接与等待 | 来源 operation/attempt、产物 ref/digest、提交与准入回执、下游接收者；等待原因、下一责任人、唤醒事件及适用期限 | Worker 提交，runtime 准入；接手按 handoff 合同记账。超期后 Supervisor 观察并唤醒有授权的恢复入口。 |

在 Run 创建前按 request/revision 展示建议或获准分工。Run 创建后通过正式关联凭证接入执行记录。UI 打开成员或看到工件，不会给该成员增加 Board、工作区、宿主或证据的权限。输入用 212 的索引按职责切片交付；原生会话和已读凭证仅在其原绑定继续有效时复用。按需查看完整消息、工件和会话时执行现有访问检查。

每项**必需义务**应有当前有效结果，或有权批准的替代/豁免。可选成员退出要记录原因和覆盖去向。阶段运行中增补成员必须关联新证据、范围、容量及受控变更。冻结后的 Candidate 如改变验收范围、目标或成员合同，必须形成新授权版本并逐项判断旧证据的适用性。撤掉持反对意见的 Reader 不能消除原 finding。

断点重启后，先按已准入的阶段版本重建名单，再按绑定对账未派发、在途、未准入和已交付的工作。新 attempt 或替换实例追加历史；同一触发最多产生一次有效派发。重连中的 provider 标明「待核实」及最近观测时间，恢复进程再次看到同一回执不重复计数。保留旧 Run 的既有读路径；缺少已批准名单时显示「历史名单未记录」，只能报已观测的执行。

## 5. 每个 Stage、Task 和 Agent 怎样展示

**打开 Run 即可见所有活跃阶段；进入任一阶段，默认视图就是该阶段的工作和成员名单。** Plan 的名单自分工准入起完整可见。已选未派发、已交付和等待汇总者都占一行。单任务列表直接显示阶段、状态和实际执行者；详情再展开当前 attempt、证据和交接。多个阶段同时活跃时可并排查看，用户无需先进入全局 Agent 列表逐个查找。

以下为示意，不代表真实 Run 状态。Plan 阶段共 4 名成员，3 项专家输入已收到 1 项。

| 成员职责 | 实际实例 | 该成员正在做什么 | 最新进展或等待 | 下一责任人 |
|---|---|---|---|---|
| OA，负责正式 Plan | oa-1 | 等待汇总 | 产品意见已收到，等待架构和身份意见 | 两名专家交付后唤醒 oa-1 |
| 产品专家 | product-scan-1 | 已交付 | 验收清单已准入并交给 OA | oa-1 |
| 架构专家 | tech-scan-2 | 执行中 | 32 秒前更新依赖分析 | tech-scan-2 |
| 身份集成专家 | 实例待绑定 | 就绪待派发 | 已等待 2 分钟，等待执行位 | WRC |

**三个方向共用同一组事实。**

- **按成员看。** 阶段行显示职责、实际实例、当前 Task 或规划问题、状态、进入状态时长、最后一次可观测进展和交付对象。点成员看其操作、产物、交接和获准开放的会话。等待时显示等谁或等哪个事件；仅知道心跳则仅报告心跳。模型是实例属性，支持同一职责换模型、换实例和重试。
- **按任务看。** 默认行如「FMS-02 · Task Verify · verify-2 · 第 2 次尝试」。展开能找到上一次 Impl、交付版本、更换执行者的原因及验收回执。一项工作需要多名 Agent 时列出各自的义务、状态与结果；一个实例被复用时按当次工作身份关联。仍未绑定执行者就显示「待分配」及调度责任人。
- **按交接看。** 记录派给谁、何时领取、交了什么、下游是否接收。Web 在协调对话旁提供成员、交接消息和依赖/沟通关系入口；CLI 在 Run 摘要中呈现活跃阶段和阻塞项，可展开成员/Task、消息和详情。CLI 操作者只读入口与 Web 共用投影。现有 `zf artifact board --attempt` 继续服务有凭证的 Worker 通信；公开 brief、提及、已读和接手保留各自语义。[角色通信入口](../../../src/zf/cli/artifact_board.py) · [Board 权限与成员](../../../src/zf/runtime/workflow_board.py)

**状态和计数口径**

| 观察对象 | 可显示的事实 |
|---|---|
| 分工和义务 | 待 OA 决定、已提议待准入、已获准、等依赖、就绪待派发、已派发待领取、已交结果待准入、结果已准入、已替代/撤销。分别显示负责决策的 OA、等候的资源或证据、实际执行者及正式签署人。保留状态原因、时间及来源。 |
| Agent 与 attempt | 实例待绑定、启动/重连中、执行中、等待输入/授权、尝试已结束、失联待核实。一个实例在线不能把对应任务推进一格。 |
| 阶段进展 | Plan 按约定的必需规划输入与正式 Plan 审批分别计数；Impl 和 Task Verify 按业务任务分开计数；Candidate 同时显示有效判词数/必需 Reader 数、判词分布和未覆盖义务；Judge 与交付分别显示回执。缺少分母就标「总数未知」。 |

例如 Candidate 显示「7/8 份判词已准入；reader-6 等宿主证据 4 分钟；责任人：受控宿主执行器」。已准入的拒绝票也进入判词计数，另列其 finding 和处理责任。Impl 和 Task Verify 分别按当前任务图代次和阶段内的 Task ID 去重，分子取与当前合同及目标版本绑定的相应阶段准入事实。一个 Task 的两位协作者、三个 attempt 仍只计一个 Task；成员义务另行计数。Candidate 则按冻结名单的必需 Reader 义务去重。成员已交付只代表该项义务的状态，整组的汇总、独立评审和业务通过各有自己的完成条件。

读模型先枚举当前获准版本的全部义务，再按其绑定关联执行记录，保留尚无 operation 的行。未能证明隶属关系的 operation 单列为「归属待核实」，不能凭显示名或时间接近补配。Run 前的提议不进入已准入分母。工作持续时长从被观测到的状态转移起计算，最后活动另设时间戳；静默本身不足以断定 Agent 已失联。

Web 与 CLI 对同一 request/revision、Run、generation 和账本快照给出相同人数、义务数及状态。加载延迟、部分投影、无权访问和无历史证据要可区分；刷新和翻页不能拼接不同代次。摘要先加载，详情按成员或任务读取。消息关系图显示沟通；任务依赖、正式采纳和裁决须从相应绑定事实取得。[按需读取与快照核对](../../../web/src/components/workflow/useWorkflowExecutionSummary.ts) · [阶段卡](../../../web/src/components/workflow/WorkflowExecutionStageNode.tsx)

## 6. OA、Run Manager 与 Supervisor 的取舍

**建议试点「OA 负责工作与恢复策略，Supervisor 独立监督，运行诊断按需唤起」。** 候选调整只涉及 Run Manager Agent 是否常驻、哪些问题需要模型判断。WRC 继续推进正常工作流，Run Manager runtime 继续跟踪恢复。适用的 OA 检查点可由 Kernel 直接请求，已获准的恢复可直接执行；两条路径都无需先找 RM Agent 转发。保留常驻 RM Agent 的项目仍可由它承接已注册的诊断请求。[199 的路由边界](../199-worker-failure-recovery-and-role-handoff.md#L114) · [200 的职责划分](../200-agent-recovery-ownership-and-unified-runtime.md#L75)

### 6.1 哪些职责有重叠，哪些需要保留

| 责任方 | 何时介入 | 应交付什么 |
|---|---|---|
| OA（角色 Agent） | 批准范围内需要确定阶段分工，或故障要求改变任务策略、验收解释、跨任务依赖时 | 绑定当前合同和证据的决定，说明复用哪些结果、由谁补证或修复、是否需要 Planner 局部改计划。工作按第 3 节并行，验收由独立角色签署。 |
| RM Agent／获准的运行诊断专家 | provider、宿主或控制面故障需要查因或修复时可直接受派，无需等待 OA 初诊；已批准方案足以执行时无需调用 | 带证据的诊断；有修复授权时执行或委派限定修复，并交回探针结果。仍未知时写明缺失证据和下一责任人。发现必须改变任务合同则带原案卷移交 OA。 |
| Run Manager runtime | 运行异常需要协调，或存在尚待验证效果的恢复动作时 | 建立并跟踪恢复请求、消费者、期限、效果与下游接手。按既有策略请求受控执行。记录中的 `owner_route=run_manager` 可指此协调入口。 |
| Kernel／WRC | 正常工作就绪、恢复已获准或重启需要对账时 | 按合同、权限、版本、容量和租约绑定 operation 与 attempt。通过相应受控入口执行，复用有效回执，按作用域继续派发。 |
| Supervisor／watchdog | 请求无人领取、处理超期、恢复者失联，或预期效果迟迟未出现时 | 记录可核查事实，触发有权限的接管或升级。覆盖 OA、诊断专家和 RM runtime 自身故障；合法等待列明责任人和唤醒条件。 |

应省掉的是**同一恢复步骤的重复分诊**。例如冻结候选同时发生宿主缺证和验收条款争议，诊断专家可查宿主，OA 可同时判断条款。已有宿主回执直接随原案卷移交。只有下游实际接手，或形成有责任人、有唤醒条件的合法等待，交接才有着落；修复效果还需由原失败探针或对应的独立验收证明。[200 的交接合同](../200-agent-recovery-ownership-and-unified-runtime.md#L343)

### 6.2 来自 LS-v1 和 8×8 的选择依据

- **LS-v1 暴露了派发责任的缺口。** 四项恢复动作已准入，RM 的 tick 也在更新，旧的 Run 级人工等待仍使下一动作为空。FMS-02 先前已收到 OA 指导。此例要求 runtime 按等待的作用域调度，Supervisor 追踪已准入动作是否被领取；多一次模型建议无法解除旧等待。[现场快照与事件](../199-worker-failure-recovery-and-role-handoff.md#L65)
- **8×8 证明两种能力都用得上。** 15:21 UTC 获准精确重建一个扫描子任务，15:25 新 product-scan 产物获准。另一个 tech-scan 在 RM 会话重启后恢复，须计入人工介入。后续 Candidate 出现混合判词时，OA 收到 8 路结果和 19 条宿主回执，才作出限定原 16 项任务范围的重规划决定。这些记录支持保留运行修复专长和 OA 语义决策；关闭常驻模型后的无人交付仍需单独实证。[扫描修复](../../impl/eight-by-eight-unattended-qualification.md#L68) · [重启后的恢复](../../impl/eight-by-eight-unattended-qualification.md#L94) · [OA 决定与准入](../../impl/eight-by-eight-unattended-qualification.md#L231)

### 6.3 关闭常驻 RM Agent 前须验证的交接

现有实现中，一类耗尽恢复的 Reader 在启用常驻 RM 时交给该 Agent，禁用后会请求 Autoresearch。Candidate 的 OA 回传无效或超时也可产生诊断请求。两者都要追到消费者实际接手。Plan 前尚无业务 Task，此时的故障需保留需求或 Run 的身份；当前要求有效 Task 的语义失败入口有自己的适用范围。[Reader 开关对照](../../../tests/test_run_manager_diagnosis_consumer.py#L125) · [OA 回传故障](../../../src/zf/runtime/candidate_obligation_followup.py#L172) · [语义失败准入](../../../src/zf/runtime/orchestrator_agent_semantic_failure.py#L45)

迁移前逐条列出原由常驻 RM 消费的请求、按需消费者、所需权限、回执和超时出口。复用同一案卷与已签发动作；重启后的迟到回复须核对原身份和版本。OA 或诊断者失联时由独立监督路径触发替代；没有获准消费者时明确升级给能决定的人，无关任务继续。第 7 节验证恢复实际完成，第 8 节决定适用的 PRD 配置是否切换。

## 8. 试点、放行与回退

1. **先交可见性。** 在固定模板和历史回放上核对成员、任务、状态与日志。先让操作者能看清卡在哪里，再评价角色数量是否合适。
2. **再验证选择。** 在新批准的 Run 中比较固定双扫描与按需 Plan，记录选人理由、每项必需要求是否有责任人、计划遗漏及补读、派发到首个有效结果的时长。用相同验收合同衡量小需求和跨领域需求。
3. **最后验证恢复策略。** 固定输入、基线、权限、模型、容量、故障和验收合同。A 组显式启用 OA 与常驻 RM Agent；B 组使用同一 OA，关闭常驻 RM Agent 并配置获准的按需诊断消费者。两组均启用相同的 WRC、RM runtime 和 Supervisor，在各自 Run 中保存实际生效的角色配置及专家调用。先做确定性故障回放，再用获准的真实 8×8 窗口验证从 Plan 批准到 Candidate、Judge 和交付的完整链路。
4. **放行由结果决定。** 两组分别报告批准后人工介入次数、每案模型交接次数、首个有效恢复动作耗时、无主等待及持续时长、任务完成、验收覆盖、Judge 和交付结果。初始批准之外的重启、手动重派、重规划或接管均单列；不得将有人干预的窗口计为无人通过。只有 B 组在约定场景下独立完成、覆盖与交付质量达标，并减少重复交接，才提请变更默认配置。样本不足或结果相反时保留原默认，按需组队与工作台可独立使用。
5. **回退按 Run 边界执行。** 新 Run 可回到原模板和诊断策略。运行中的 Run 沿已接纳版本继续；必要的变更走现有受控代次或恢复入口，保留原分工、失败、已准入证据与人工干预历史。
