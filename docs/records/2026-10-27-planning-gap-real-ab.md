## 阻塞原因已定位

先做不读项目、只返回固定文本的最小真实调用：

1. 当前 `mcp/playwright` 镜像默认用户为 node，而旧评估器把认证和临时目录放在 root 下。
   显式容器用户和临时可写 root 目录修复启动权限问题；项目、认证和容器根文件系统仍只读。
2. 镜像缺系统 CA bundle。Node 的自带 trust store 可连接域名，但 Codex 原生 TLS 无法
   完成模型/工作区路由发现。只读挂载主机 CA，未关闭 TLS 校验。uv Python 的 cafile
   可能为 None，实际 bundle 在 capath 下，评估器也覆盖该情况。
3. TLS 修复后，旧 `gpt-5.4` 明确返回 `model_not_found`，说明当前 ChatGPT 账号不支持。
   本轮两组统一采用本机配置的 `gpt-6.1-terra`。不是把上次无输出的失败试次拿来比较。
4. `--timeout 0` 支持无墙钟截止；本轮未以 600 秒截断。连接/模型错误仍算失败，不算通过。

最小成功探针 16.98 秒，返回 `AB_CONNECTION_OK` 和 turn.completed；修好 CA 后对旧模型
再做隔离探针，确实得到 400/model_not_found，保留了因果区分证据。期间发现 uv CA
解析差异的失败批次没有输出，被明确排除评分，未覆盖或删掉原日志。

### 严格评分的敏感性

盲评分认为旧版两次没有明确讲清：

- R4/A6b：只指出 source_index 的任务摘录和覆盖映射不足，修订说“从原始需求独立
  建立来源覆盖账本”，没有明确分离“独立来源全集”和“覆盖账本”。
- R5/A6c：说 items 是输入文件，并讨论“一张页面不能证明全部行为覆盖”，没有明确
  反驳“一个输入文件等于一张页面”的计数错误。

人工复核认为，这两份旧输出的修订也部分表达了来源独立/页面与文件分离的意图。
若采用较宽的语义命中口径，旧版也可以计 24/24。原始盲评分和这份敏感性分析同时
保留，**不把 22→24 当作稳健的识别能力提升证明**。两组对主要执行缺陷都判断正确。

新版三次都具体指向 `coverage_ledger`、独立来源全集及页面/表单字段；旧版更多给出
“正式受控端口”“来源覆盖账本”的一般修订。这个质性差异与新增作者契约一致，说明
交接建议更明确；它不是预先注册的额外得分，也尚未证明 Planner 会产出正确 Package。

## 评估结论与下一步

- 上轮环境隔离、回收和 Preview 投影改善已有独立的修改前后故障复现；本轮补齐了
  真实模型调用证据，不能把这些不同层级的结果合成一个“产品通过率”。
- 新方法没有在样例中增加误报或弱化原需求；端口修订表达更稳定。这支持保留精确
  作者契约和已验证代码修复，暂不支持继续堆叠大量语义提示。
- 当前样例有天花板效应：旧模型/旧 skills 本来就能发现主要问题，prompt 也明确提供
  当前 route。三次重复不是三个独立业务；样例围绕已知故障设计，不是未见过的 holdout。
- 下一项有价值的验证是冻结一份未见 PRD，分别从空白生成 Plan/Task Map，检查真正
  输出的 producer/blocked_by、局部/最终验证责任、来源端口和 Preview 解析结果，再看
  Critic 返工轮数。最终还要以批准后的 Impl/Verify 执行验证交付效果。

因此，本次可以关闭“真实 A/B 尚未跑通”的验证项；不能关闭“完整产品 build 已证明
更好”这一尚未执行的研究问题，也不自动批准现有 FMS 计划。
