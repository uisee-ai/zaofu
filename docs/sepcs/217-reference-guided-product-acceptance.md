# 217 · 需求调研、候选产品对标与任务执行看板

> 状态：已实施，真实试点逐项验收。核对基线为 ZaoFu `dev@e1f363c4`。[实施与验证记录](../impl/217-reference-acceptance-validation.md)

## 1. 要解决的问题

LS-v1 的车辆质保在原始 PRD 中有独立时间线、增删改查和权限要求。覆盖表将它标为已覆盖，原任务被取消后，后继任务只承接了通用车辆验收项。历史浏览器复盘从车辆详情点击“质保”，得到“此分区暂时不可用”。当时的调查可在 LS-v1 仓库的 `docs/records/2026-11-20-requirements-gap-review/review.md` 第 6 节核对。

本规格的交付目标是让造父在已授权的无人监工运行中，能解释哪些外部做法被采纳，在集成产品上证明用户能完成原始需求中的任务，并让操作者随时知道一项工作由谁执行、取得了什么进展。产品是否达标取决于当前候选上的实际行为。任务数量单独统计。

## 2. 从讨论到候选验收

```text
Kanban Agent / Channel 收到需求
  └─ 围绕待决问题复用资料或检索 → 记录采纳决定、适用范围和来源
       ├─ PRD Preview  · 用户、场景、预期结果、取舍
       └─ Plan Preview · 对应条款、Task、独立验收责任与证据
               ↓ 现有审批与冻结
          各 Task 实施 → 独立 Task Verify → 集成并冻结候选
               ↓
          Candidate Verify 在统一入口验证已登记的跨任务场景
               ↓
          独立复扫对照原始需求、已批准决定、候选行为与已有证据
               ├─ 已承诺且有反例 → 定向修复 → 新候选复验
               ├─ 证据不足       → 补证或诊断 → 原断点续行
               ├─ 新发现的能力   → 待评审 backlog
               └─ 既定范围已验收 → 按当前流程进入 Judge / 交付
```

PRD v5 在候选验收后由独立 Discovery 复扫。范围内的缺口产生可派发的 gap task 后，沿现有计划增补路径推进。有开放缺口却没有可执行下一步时，保留阻塞及责任。目标关闭后触发 Thin Judge，最终交付遵循该 Run 的交付策略。其他 Workflow 依其实际路由承担这些责任。OA 在授权范围内提出分工和恢复建议，Kernel 校验绑定并执行受控动作。[PRD 工作流定义](../../src/zf/core/config/workflow_profiles.py) · [Discovery 差距分流](../../src/zf/runtime/orchestrator_module_parity.py)

### 2.1 讨论期怎样检索，怎样采纳

Kanban Agent 或 Channel 先读用户材料、指定模板和已有决定。某个未知项会改变产品行为、技术选择或验收标准时，提出具体问题。例如“审批人拒绝后，提交人能否修改并保留历史记录”。按问题选取可比较的产品、GitHub 代码、官方文章或论文。记录参考版本或查阅时间、观察到的行为、适用条件、局限和备选方案。能回答问题时结束检索。原有结论仍适用时直接复用。单独启动 Research 工作流时沿用当前请求版本、授权和结果返回入口。[现有调研与采纳路径](../../skills/zf-research-fanout-trigger/SKILL.md) · [现有设计调研方法](../../skills/zf-plan-execution-readiness/references/design-research-handoff.md)

对影响交付的参考逐项说明“采纳、调整后采纳、舍弃或待定”及理由。明确原始要求和已批准的修订优先。用户指定 UI 模板时，记录适用页面、交互和允许的差异。外部设计若改变这些约束，走既有变更路径。用户研究、Agent 实测、厂商声明和推断应分别标明。

| 交接位置 | 下游应从现有产物中读到的内容 |
| --- | --- |
| PRD Preview | 用户与模块、具体场景、预期结果、采纳理由、来源/版本、有意保留的差异。尚待决定的事项列出影响范围。 |
| Plan Preview | 原始条款与采纳决定、实现 Task、独立验收者、实际入口及证据。必验场景和断言进入已有 `product_acceptance_spec`。 |
| Task 交接与替换 | 指向同版来源、适用于本任务的决定和验收责任。取消、拆分或替换 Task 时，逐条说明后继承担的义务或已批准的范围变更。 |

首版使用正文与既有引用，让两份 Preview 从各自读者的角度呈现同一决定。计划批准后，各 Agent 按任务读取所需来源。完整调研材料保留引用，供需要时追查。[PRD Preview 正文](../../web/src/components/channel/ChannelPrdPreview.tsx) · [Plan Preview 原文](../../web/src/components/delivery-trace/PlanReviewReader.tsx) · [Planner 的验收合同](../../skills/zf-prd-plan-synth/SKILL.md)

### 2.2 合并后怎样对标与补差距

对标时间是相关 Task 集成为固定候选之后、最终交付之前。以模块组织，以用户要完成的工作比较。沿用选定参考的版本、角色、起始数据、操作及预期。需要解释新差异时可按问题补查，并注明新增依据。引用的新版本与批准基线分别记录，避免同一轮验收的标准随搜索结果漂移。

| 对标对象 | 可复核的证据示例 |
| --- | --- |
| UI 与交互 | 指定模板、相同视口/状态/数据的截图，加真实入口的操作断言。记录视觉差异及影响。 |
| 业务旅程 | 在统一入口按角色操作。以质保为例，管理员新增并编辑后刷新可见，只读用户可看、写入被拒。按源条款另验删除和时间线。 |
| API、架构与可靠性 | 以相同输入核对接口契约或状态结果。对持久化、重试、恢复等已承诺属性，保存中断前后读数或失败探针。 |

Candidate Verify 对固定候选检查已登记场景。独立复扫从原文逐项反查当前验收责任和证据，也从候选行为反查批准依据。这样即使 Planner 漏登条款，复扫仍有独立输入。有效证据按已证明的断言复用。发现新反例或未覆盖风险时追加探针。Thin Judge 消费已准入的结论。[候选验收合同](../../src/zf/runtime/product_acceptance.py) · [原始目标复扫与返工](../../skills/zf-verify-rescan-replan/references/product-convergence.md) · [产品 E2E 设计](../design/201-product-acceptance-with-e2e.md)

| 差距与判据 | 责任与下一步 |
| --- | --- |
| 原文或已批准决定有要求，候选上有可复现反例 | 复扫记录稳定 finding、来源、受影响场景、候选身份、预期/实际与证据。沿既有 gap/replan 路径提交最小修复。如需补登漏项，修订验收规格并走其授权路径。 |
| 缺账号、环境、必读来源或必要证据 | 记录未验范围、诊断或补证责任人和恢复条件。必验项保持待验，满足条件后恢复对应尝试。 |
| 竞品存在额外能力，原需求未承诺 | 记录用户价值与证据，作为待评审候选。既定范围可以继续交付。例如质保到期提醒只有在已获采纳时才纳入本轮验收。 |
| 实际差异符合已批准取舍 | 引用取舍与适用版本，结束该项对比。 |

断点后复核 Run、Task Map 代次、候选提交、验收规格引用及摘要。绑定仍有效时继续未完成场景。候选或条款变化时判断受影响范围，留下证据复用依据并对新候选重新取得所需结果。相同 finding 与已有修复任务关联。产品结论注明哪些来自 Agent 实测、哪些来自真实用户验证。[候选运行与规格绑定](../../src/zf/runtime/product_acceptance.py) · [上下文与恢复设计](../design/198-context-index-write-read-resume.md)

## 3. Kanban 卡面的过程状态

卡面优先显示当前阶段和状态、当前执行实例、最近有效产出及时间、等待对象或下一动作。归属人、计划分配、实例在线和验收结论各有独立含义。只有当前执行绑定才能显示为在执行。排队、暂停、已退出及未观测可直接说明。下面是卡面示意。

```text
车辆质保 · Task Verify · 等待测试账号
本次尝试    verify-lane-2 · 第 2 次
最近产出    14:10 已验证管理员修改后刷新仍可见
等待条件    只读账号可用后，继续验证写入被拒
```

同一 Task 有多个活跃成员时，卡面显示实际人数和角色，详情列出各自义务、尝试、产物和交接。心跳只更新在线时间。邮箱回执可表明消息已送达，验收结论取本阶段正式准入的结果。重试保留历史尝试，依当前绑定统计活跃实例。Run 级 Candidate Verify / Judge 从卡面链接到所属 Run。无运行绑定的普通任务显示 TaskStore 中的状态。卡片和详情按同一代次和观察时点投影，列表只取摘要，展开时再读证据正文。[当前任务卡](../../web/src/components/kanban/TaskCard.tsx) · [现有工作流任务详情](../../web/src/components/workflow/WorkflowTaskDetails.tsx) · [普通任务详情规格](../specs/kanban-task-detail.md) · [215 阶段工作台](../design/specs/215-oa-stage-teams-and-execution-workbench.md) · [216 交接回执](../design/specs/216-durable-agent-mailbox-and-handoff.md)

## 4. 实施分工

| 顺序 | 改动位置 | 完成条件 |
| --- | --- | --- |
| P0 · 讨论与交接 | 扩展既有讨论、需求对账、Planner Skill 和交接样例 | 从真实入口发起的需求，在两个 Preview 读到同一采纳决定，并能追到负责实现和验收的 Task。 |
| P0 · 候选对标与复扫 | 扩展 Verify / rescan Skill，沿用现有验收与增量返工合同 | 同时证明能找回漏登的原始条款、能处理证据未知、能让范围外机会留在 backlog。 |
| P1 · 卡面 | 改 Kanban 前端，复用已有任务与阶段执行投影 | 卡面和详情对同一尝试显示一致事实。仅在列表缺少必要字段时增加批量只读投影。 |

实施时检查角色实际加载的 Skill、收到的输入、正式结果和调用入口。发现某条启用路径漏加载方法、漏传当前引用或允许旧绑定通过时，以复现用例修相应配置或代码。语义判断归 Agent。授权、版本、证据绑定、状态转换沿用既有 Runtime 合同。以上改动均可在原有阶段内完成。

## 5. 验收与无人监工试点

| 场景 | 操作与可核验结果 |
| --- | --- |
| A1 · 参考进入预览 | 从 Kanban 和 Channel 分别走现有入口，一例采纳参考、一例复用已有结论。核对来源/版本、采纳理由、对应条款与 Task。能在两份 Preview 找到各自责任。 |
| A2 · 原始需求漏登 | 构造车辆质保最小夹具，原文要求明确，故意从计划验收表删去该项，候选只有标签且入口报错。从这份冻结历史输入回放，检查独立复扫能定位原文及行为反例、派生定向修复，并在新候选取得全套质保断言证据。 |
| A3 · 已登记但漏证 | 保留必验权限断言，提交缺少该断言结果的候选报告。核对既有准入拦截。账号不可用时记录待验与补证责任，账号就绪后有同场景的执行结果。 |
| A4 · 竞品独有能力 | 在参考中提供本轮未承诺的到期提醒。核对其进入待评审 backlog、原有验收范围可正常收口。 |
| A5 · 断点与变更 | 在补证或修复派发后中断并恢复。核对有效绑定复用、同一 finding 只关联一个有效修复。更换候选或规格后，旧结果不能直接签收当前候选。 |
| A6 · 看板准确性 | 在浏览器查看排队、并行、重试、等待、终止和运行级验收。持续心跳期间最近产出时间保持原值。点击卡片定位当前尝试、关联 Run 及已绑定证据。 |

先用可重复夹具验证路由与拒绝条件，再用真实 Provider 从批准后的最小输入运行至交付或具名阻塞。仅已有授权范围内的动作可自动推进。记录 Run、输入/候选版本、finding、修复与复验回执、是否发生人工介入。无人监工成功用例须有当前候选的实际交付结果。停在合理授权点的用例单列。A2 如由人指出遗漏或手工补写验收结果，记录为人工介入样本。A6 保留实际浏览器断言与截图。以上均是实施后的验收条件。
