# 214 · Workflow Skill 任务评估与按需加载优化

Task Verify 首批四阶段已实施。历史回放、在线评分和独立复核已接入任务页。首个加载策略试点在 Codex 上完成 42 次隔离运行，保留测试集未达到采纳门槛，Verify 继续默认必读。Claude Code 的实际效果待独立验证。[操作入口与试点数据](../impl/214-task-verify-skill-evaluation.md)

## 1. 两个决策

1. **这个 attempt 的职责履行得怎样？** 每次任务阶段结束后生成有证据的评估卡。卡片回答哪些 Skill 可用、哪些有调用见证、相应方法要求是否得到满足，以及问题归谁修。
2. **下一版还需要默认加载这个 Skill 吗？** 在相同冻结输入下比较现行、按需和移除方案。按角色、任务类型、模型与执行客户端版本给出保留、精简、改为按需或退出的建议。

8×8 复盘中，原 Run 的 60 份冻结方法包按名称去重有 34 个 Skill，按“读取命令指向物化文件且工具返回含该 Skill 文头”的保守口径能确认 28 个至少返回过一次。Task Verify 的部分简报指标列出零个自动项，同一角色的指令和工具返回却能定位到实际方法。历史频率适合选案例，单次成功或未见调用都不足以决定删留。

骨架继续负责身份、权限、目标提交、输出协议、证据绑定、独立验证和恢复。可以调整的是派发给模型的说明、示例、索引和方法加载策略。模型或 Codex / Claude Code 升级后，重新测量该组合。架构边界沿用[运行时职责约定](../../AGENTS.md)与[工作流输入及恢复规格](../design/212-workflow-artifact-reading-and-session-resume.md)。

## 3. 谁来评，何时评

| 职责 | 输入与产物 | 权限 |
|---|---|---|
| 确定性评估器 | 异步消费阶段的权威终态，包括通过、已准入的 blocked、失败或取消。核对绑定和机械指标，先出卡；原因不可辨时保留未知。 | 读取冻结证据，写评估专属记录。评估失败可独立重试，业务派发、重试和交付照常推进。 |
| 按需独立评审 Agent | 对业务义务是否满足、证据冲突、疑似关键误放行及策略抽取的正常样本逐项复核。输出裁决、证据、局限与优化建议。 | 使用独立只读会话；绑定评审者、版本、规则和输入摘要。被评 worker 及参与本次处置的 OA 不担任该次独立评审。证据不足可弃评。 |
| Orchestrator Agent（OA）与 Evolution | OA 查看跨任务趋势，提出待验证的方法改动。Evolution 在获准范围内运行配对实验、管理候选版本和 canary。 | 任务原判词由原业务角色负责；采纳沿用已有准入和回退路径。只有新派发接收获准的新方法包。 |

评审的预算、正常样本抽样率和触发原因随策略版本记录。预算耗尽或评审服务不可用时，卡片保留已有事实和待评项。抽样复核应包含通过与阻塞两类，并保留入样原因，以便区分专项排查结果与总体表现。阶段 3 实现以盲评方式将独立观察与原判词比较。校准同时披露漏报的关键误放行和证据不足引发的误报，评分修订可追溯到原义务和宿主观察。

## 4. 任务卡数据合同

每个阶段 attempt 一张逻辑卡，每张卡有零至多条 Skill 记录。任务页按 attempt 展示 Impl、Verify、返工与重派，任务结果和整轮成本在卡首出现一次。JSON 是机器可读产物，Markdown 或任务页从同一数据渲染。

| 字段组 | 必备内容 |
|---|---|
| 身份和版本 | schema 版本、workflow run、task 或工作流操作、operation、attempt、dispatch、角色、output profile、目标或输入摘要、合同与 rubric 版本、终态事件引用。记录模型、Provider、Harness 名称与版本、简报及冻结方法包摘要；缺失项显式标记。 |
| Skill 行 | Skill 名、包摘要、加载策略、适用性（应使用／可选／不适用／未知）、可用性、调用证据与读取返回证据分别记录。一个成功读取只证明相应内容曾返回。 |
| 行为评分 | 稳定的 criterion ID、适用义务、判定来源（机械检查／独立语义评审）、结果、是否关键、证据引用和理由。多项 Skill 共用一个行为证据时标注共同观察；重复引用不会增加任务层的通过数。 |
| 任务结果及成本 | 正式裁决引用、首次有效提交、返工、正确阻塞或误放行的证据，及实际可测的时间、调用和 token。能绑定到具体 Skill 的读操作可单列，其余成本留在 attempt。 |
| 优化建议 | 对象（Skill／prompt／profile 说明／证据生产方／观测链）、适用范围、问题证据、建议改动、验证正反例。缺少证据时写清需补什么。单卡的因果增益标记为 `unmeasured`。 |

**评分规则。** 单项可取 `pass`、`fail`、`unknown`、`not_applicable`。履职分为 `100 × pass / (pass + fail)`，同时显示分子、分母、未知和不适用项数。分母为零时返回 `null`。已确认适用项的可判定覆盖率单列为 `(pass + fail) / (pass + fail + unknown)`，适用性本身未知另列。任何关键误放行单列告警；关键项仍未知时，摘要显示“待证”，即使其余可判定项全过。每条有分数的业务判断应能追到相应义务与证据。

**示例。** 下例为 Task Verify 风格的 JSON 展示节选，标识为示意值。它取材于 8×8 Candidate Verify 的浏览器案例：命令成功并归档了 9 个文件，合同声明的目录却未能精确绑定验收义务。验证者正确阻塞，可判定其履职；单个 Skill 的增益仍待实验。

```json
{
  "schema_version": "skill-attempt-evaluation.v1",
  "attempt_id": "example-verify-1",
  "task_outcome": "blocked",
  "criteria": [
    {"id": "block_unbound_evidence", "result": "pass", "critical": true,
     "evidence_refs": ["example-contract", "example-host-receipt", "example-admitted-verdict"]}
  ],
  "score": {"passed": 1, "failed": 0, "unknown": 0, "not_applicable": 0, "percent": 100},
  "skills": [
    {"name": "zf-yoke-test-evaluator-role-context", "invocation": "unknown", "lift": "unmeasured"}
  ],
  "recommendation": {
    "target": "evidence_producer",
    "change": "归档时把每条浏览器验收义务绑定到实际文件和摘要",
    "verify_cases": ["有归档但缺映射，应继续阻塞", "映射完整，应进入内容审核"]
  }
}
```

**重放与迟到证据。** 以 run、operation、attempt、dispatch 标识逻辑卡；同一终态、规则版本和证据集合重复消费产生同一版本。后到的工具返回、正式语义评审或规则修订生成新版本，引用前版及变化原因。并发消费者须幂等发布，断点后可补卡。旧版本可复查；查询和回填使用原冻结包，缺失证据保留未知。证据引用继承原访问范围，渲染面展示脱敏摘要；评审不能通过任务卡获得额外的原始轨迹权限。

## 5. 用配对实验决定保留、精简或退出

首个候选为 Task Verify 的 `zf-project-adapter-matrix-enrichment`。它在 8×8 验证角色中默认加载，适合检验“已有完整合同的任务是否仍需这项方法”。这是一条待验证假设。

1. 从冻结案例构建三类场景：合同完整的普通任务、确实需要补矩阵的任务、证据存在但与义务绑定错误的任务。另保留无关请求测试误触发；优化器接触训练集，选方案用选择集，最终采纳用未参与修改的测试集。
2. 按同一案例及重复序号比较三组：移除目标 Skill（raw）、现行自动加载（current）、相同内容改为按需（candidate）。固定其他方法包、输入、简报中无关内容、权限、模型、客户端版本及预算；各组使用隔离会话。精简正文另开实验，一次只变一个因素。
3. 分别报告自然触发、漏触发、误触发、关键漏检、误放行、正确阻塞、误阻塞、首次有效提交和实测成本；标明有效配对数、缺失与超时。强制读取可单独验证正文效用。Codex、Claude Code 及不同模型版本独立报告。
4. 采纳前预先固定质量容差与成本目标，沿用现有可比性、路由压力和覆盖门槛。当前持久采纳代码下限为至少 3 个不同案例、每例每组至少 2 次，仍须满足已配置的更高门槛。若关键负例发生误放行，或样本不足以支持结论，则保留现行配置并报告原因。只在质量与覆盖达标后比较成本，给出适用范围、灰度版本和回退目标。[采纳声明实现](../../src/zf/runtime/evolution_skill_claim.py)

prompt 也要独立做减法。8×8 留存的最大 Planner 简报为 78,963 字节，其中输入清单占 37,587 字节，Skills 区占 3,844 字节。优先比较“完整清单”和“短入口加按需正文”，保持必读义务和输出协议一致，按实际 token、读取次数与验收结果评估。这个实验独立于前述 Skill 加载实验，避免把清单缩短的收益归给 Skill。

## 6. 分期与验收

| 阶段 | 可验收交付 |
|---|---|
| 1 · 只读回填 | 用冻结 8×8 记录生成 Task Verify 卡，同一 lane 的不同任务/attempt 不串证。覆盖正确阻塞、关键误放行、不可判定三个案例；历史缺少误放行正证时使用标明为构造的负例。缺回执显示未知，同案重放结果一致。 |
| 2 · 在线异步出卡 | 验证通过、阻塞、失败和取消都能查询卡片；重复终态、并发补卡、运行中断、迟到证据可复现。停掉评估消费者，业务仍可推进，恢复后补齐卡片。JSON 与任务页的分子、分母、证据和修订一致。 |
| 3 · 独立语义复核 | 用冻结且含已知正反例的样本校准评审。核对与参考判定的一致项、分歧、关键误放行及弃评；评审失败或超预算显示待评。证据生产方的问题能被归到生产方。 |
| 4 · 优化试点 | 产出首个 Skill 的三组配对报告，列出按模型/Harness 分开的质量、成本、有效样本和采纳理由。验证灰度可回退、旧 attempt 重试保留原冻结合同。证据不足而没有发布候选，也是有效的实验结果。 |

首批完成条件是 Task Verify 的卡片可回放、可复核，并能支持一次有可比证据的加载策略决策。推广到 Impl、Candidate Verify 和 Judge 时，各自定义少量角色专用评分项，沿用同一张卡与身份绑定规则。
