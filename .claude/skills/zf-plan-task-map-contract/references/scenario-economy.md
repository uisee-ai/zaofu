# 最小完备场景集

使用既有 `test_matrix.tests[]` 字段与 command registry；本方法不引入新 schema 或
运行时“相似度去重”。由 Planner 判断等价性，Critic 检查反例。

1. 先列来源规则、失败不变项、边界与各片/最终验收责任；每项有稳定 source/AC ID。
2. 一行测试表达一个有区别的行为结果。相同 owner、tier、command、前态与结果的
   参数可在 `when` 明确列举，`then` 明确要求逐项验证；保留每项具体值/边界，不能
   只写“若干非法输入”。不同错误码、前态、清理结果、权限或验证阶段分别保留。
3. `given/when/then` 写本例可观察条件和结果，不复制整段来源 AC、整篇 Scenario
   或所有兄弟场景。source_ids/source_refs 指向同版原文；命令通过 command_ids 引用。
   引用不是留空场景的理由，交给执行者的本例仍须独立可理解。
4. 同一规则被 CLI 与 HTTP 验证时，分别保留两入口责任；共享失败语义在 Plan 的
   共享合同只解释一次，各片写其入口特有结果。不能把两个尚未同时存在的入口放进
   首片 mandatory task_verify。最终跨入口互读/集成另有 owner 与时点。
5. 不从所有输入维度生成无依据的笛卡尔积。列出必须组合的状态/权限/失败条件和
   原因，其余等价类明确列值；临界值、恢复/重试及“已有目标/不存在目标”不能消失。
6. replan 先核对实际变更与原 finding；未受影响的稳定 ID、命令和场景保持原样。
   共享合同改变时，重审所有受影响场景，不能凭作者“无影响”继承旧结论。
7. 完成后独立读回实际矩阵，抽查首/中/末及每类失败。记录每项来源的覆盖位置、
   独有反例、任务 owner/tier 和命令。行数/字节只做诊断，不设必须达成的缩短比例。
8. 同一 AC 在 Task Map、命令登记、验收矩阵和产品验收规格的 owner/tier/阶段须表达
   同一责任；人工阅读不能统一贴为 E2E。互补的自动断言与人工阅读分别标明生产者、
   断言及证据；既不遗漏人工义务，也不把合法的多种验证误判为矛盾。
9. 从来源中拆出当前任务实际承担的子断言，再写入序列化 AC 和测试行。整段双入口
   要求前加“本任务范围内”不会消除后继义务：CLI 片不能因此要求尚未生产的 HTTP
   实际监听或最终 README。将这些义务保留在真实生产者，稳定来源 ID 仍可共享。
   交付前读回实际 Task Map 的每条 mandatory AC 和对应测试行；只解析 JSON 或
   阅读已局部化的 Markdown 不构成一致性核对。When 写触发动作，Then 写可观察结果，
   不把同一结果句复制进各字段；参数列明实际取值及前态，不再复制上级 AC 全句。

例：同一 CLI 校验阶段拒绝未知字段 `extra` 与错误类型 `body: []`，均返回非零、
保留原 bytes 且不创建临时文件，可同一行明确列两例并逐一验收。HTTP 的相应用例
仍单列 HTTP 400 与响应体规则；临时写入失败/替换失败/损坏源文件的保护分别保留。

反例：把“缺失/非法角色被拒绝”和“合法 editor/reader 读取当前值”放进同一
Given/When，却统一写 Then=`CLI 非零` 或 `HTTP 403`，会把成功读取也写成失败。
应分开成功/拒绝行，或逐个参数分支明确对应的 0/200、非零/403、返回值和文件不变项；
不能让执行者自行猜测哪段预期适用于哪个输入。

Critic 发现合并掩盖不同责任或结果时给具体反例；作者缩短文本本身不构成通过证据。
