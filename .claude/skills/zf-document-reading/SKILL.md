# PRD / Plan 正文阅读与审查

作者与评审者共用本方法，适用于 Channel、Kanban PRD、Planner 和 Critic。
使用现有完整 Markdown、来源/决定登记与评审报告，不新增机器字段或语义门禁。

## 作者交付

完整正文的标题后先交代用户、问题、本次行为变化与范围，再解释方案、关键失败行为、
验收和确需决定的事项。PRD 沿用户流程展开需求，Plan 随后展开任务规格与共享合同。
可选摘要与完整原文都采用这个顺序；不能只修概览，让默认完整原文仍以工程审计开头。
没有独立摘要字段时直接在正文开头说明，不为排版编造用户证据、功能或审批。

来源路径、SHA/digest、事件ID和授权时间线放在末尾工程附件，正文以精确条款引用。
若授权缺失确实阻塞当前动作，在开头用一句话说明影响和所需决定，身份明细保留在附件。
所有强制范围、验收、风险、异议及当前证据状态必须保留；折叠或优先级不表示已解除义务。

场景使用独立列表项或段落，例如“GIVEN（前提）”“WHEN（动作）”“THEN（结果）”，
不靠普通软换行分隔。优先中文标题，保留既有 Requirement/Scenario/AC 标识和协议要求的
固定词。路径/命令/代码标识用行内代码或代码块；长描述使用条目，表格只组织可比较字段。
运行时已经追加的来源/决策/companion目录无需在作者正文复制全套，重大风险和待决影响
仍须在正文说明。既有原文纯重排应记录同义修订，不能直接覆写已接纳工件。

## 作者自检与独立评审

提交前读取实际落盘的完整 Markdown，按默认原文阅读路径核对开头与至少一个验收场景。
Critic 对同一候选独立执行，不能把技能已加载、标题齐全、UI摘要或作者自评当作通过。
在现有评审报告中简短记录：被审文件ref/digest、开头与场景的位置及短引文、读者能否
理解交付/验收/待决、具体缺口与处置。无场景或不适用时注明依据，不补造产品测试结果。
沿用当前报告可用的说明/证据字段，不增设固定报告格式，不重复粘贴本方法。

完整原文仍由路径/哈希主导开头、场景未能分辨前提动作结果时，指出原文反例并要求定向
修订；来源完整性、语义覆盖和证据状态同时复核。版式偏好与影响理解的缺陷分开报告，
不以固定字数、标题命中或平均分代替判断。返工后重读改动位置及受影响条款，保持有界。
未打开实际Web只称原文审查，未取得同文档Codex Desktop参考不能声称视觉对齐。

## 定位与去重

先选定每条共享行为与 AC 的唯一说明位置，再在任务中引用稳定 ID、适用范围和该任务
特有的实现/验证责任；来源矩阵只保留导航和覆盖关系，不抄写全文。跨任务失败语义写在
共享合同，任务写本片如何建立和验证它。任务独立交接时必须携带可解析的同版共享片段，
不能只留脱离上下文的 ID，也不能靠删去边界条件来缩短文档。Plan 的逐任务阅读入口
按 task-map contract：已绑定 execution_spec 的 tasks[].body.human_review.module_spec_markdown，
或原文精确二级标题 `## Task Spec: <task_id>`；共享执行规则也必须有准确引用，
不能只引用业务 AC 却遗漏另节的准备/清理。正文有任务描述不等于模块阅读入口可用。中文叙述标题表达业务动作；
schema 强制标题、命令和机器 ID 保持原样，不另造一套同义章节。

例如共同的 AC-SAVE 说明“提交失败保留草稿”；T-SAVE 引用它并说明保存与回滚的验证，
T-ENTRY 引用它并说明入口调用与重试的验证。不要在共享合同、两项任务、来源表复制四遍
同一个完整场景。先检查覆盖与责任未丢失，再精简重复。

## 来源与工程细化

从用户原文开始区分：明确硬约束、已授权决定、作者提出的工程细化。沿用既有来源索引、
决定/假设登记和 Task 规格标明类型、理由及影响，不增加第二份登记。工程细化可以给出
可执行的推荐方案，但不能伪装成用户原句、悄悄改变验收或提升为全局阻塞。需要 Owner
选择时记录最迟决定时点；已有授权范围内的普通实现选择由任务承担，不制造审批流程。
Critic 同时核对原始输入和生成 PRD；发现生成稿擅自收紧时指出上游偏差，经受控同版修订
处理，不能只逼下游遵守错误升级的要求，也不能擅自忽略当前已批准合同。

例如用户要求“各任务有 RED/GREEN，最终运行全量命令”，并不自动等于“每个任务 GREEN
必须运行全量命令”。若作者建议额外全量回归，应标明工程建议及成本/适用点；原文明确
要求每片全量时则必须保留。例子用于理解来源边界，不是任何项目的预设验收。

## 开头反例与返工证据

独立评审先读标题之后实际出现的最前一个内容块（包括表格、说明框、列表），再读后续
业务段落。报告引用最前块位置和短引文，解释它是否让读者理解产品；若先有来源/授权
台账、后有业务介绍，不能只截取后者宣布首屏通过。真正影响当前动作的风险/授权警示
可以前置，但应说明必要性；不能凭关键词命中判失败。以“来源/SHA/授权履历开篇，第二段
用户结果”为反例，与“用户及行为开篇，确实阻塞的警示一句话，来源附录”比较读者任务。

返工后的最终评审对当前 ref/digest 作结论。正文变更时重读开头、代表场景及受影响条款；
正文未变时可引用上一轮报告的 ref/digest、原文片段位置与判断，说明如何核对该片段未变，
并检查新上下文是否改变判断。最终报告明确哪些本轮重审、哪些继承、哪些仍未覆盖。
只关闭某个技术 finding、引用作者自评或写“先前已通过”都不构成阅读结论；证据缺失先补
有限复核，不默认重跑全部审查。优先在既有报告字段简短记录，不复制长报告。
