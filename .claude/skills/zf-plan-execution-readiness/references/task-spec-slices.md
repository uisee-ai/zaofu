# 从产品规格到可验收的任务切片

Planner 形成任务前、Critic 审查最终持久化包时使用。复用现有 Task `contract`、
Task Map、Plan、矩阵和评审工件，不新增任务 Schema、自动语义评分门禁或授权。
Spec 是可实现、可证伪的行为合同；字段齐全、命令存在和 covered 均不证明通过。

## 先确定行为与边界

从冻结来源提取主体、前态、输入、动作、后态、拒绝、失败不变项及恢复方式。
接口说明生产者/消费者和版本，UI 说明入口、反馈、状态及键盘行为。保留定性要求；
来源没承诺的行为、阈值、技术栈和非目标不自行补成已批准事实。必要合同未知时
登记问题、负责人、影响任务及最迟关闭点；未来决定不阻塞无关的当前工作。

按可观察结果、依赖、事务及写入所有权切片，不按文件数或凑并行度分 Task。
实现、测试、文档通常是片内步骤；同一失败事务尽量由一个行为生产者负责。
脚手架、研究或迁移任务写明可检查结果、消费者及接线入口，不冒充产品交付。
本片验证只依赖已完成前置和本片结果；未来装配结果交给具名后继的候选验证。

## 一份共享正文，本片承担明确义务

共享数据/接口/规则仅维护一个同版权威正文；场景和决定使用既有稳定 ID。
Task Spec 展开本片新增/修改行为、例外、失败不变项和责任，引用适用的共享条款。
不要复制所有决定/场景，也不能只写“见总文档”：接手者必须能取得所引用的完整
正文，并知道哪些条款约束本片。下游必要规则不能藏在不会选读的兄弟任务中。
技术步骤和历史修复过程放次级说明；实际合同不要求时，不固定内部类名和算法。

先分开规则、具体例子与未知问题；未知例子不能写成已确认结果。示例应可直接用作
测试数据：绝对 URL 要给完整合法 URL，保留原字符串与校验解析结果的区别。
“合理焦点”“正确错误处理”等需细化观察规则；未授权的取舍保留为待决定。

写作 Skill、方法文件与作者提示是过程指导，不是产品需求来源。产品正文引用实际
需求、已确认决定和业务合同；不要要求接手者取得 method.md 才能理解已冻结行为。

## 任务正文模板

```markdown
## Task Spec: <exact task_id>
### 本片结果与边界
可演示结果、对应来源及不承担的相邻义务。
### 来源与共享合同
冻结来源位置；共享合同版本、具体适用条款及可取得的正文引用。
### 行为与失败
前态/输入 -> 动作 -> 后态；拒绝、失败不变项和恢复。
### 接线与依赖
真实入口、已完成前置、Task Map 中的允许写入范围及消费者。
### 验收与早期反馈
具名场景 -> 本片 AC -> 本片命令/验证 owner/tier/入口/证据位置。
独立 Verify 与后续集成的责任、生产者和时点分别明确。
### 决定与交接
相关决定 ID、状态、负责人、关闭点；本次修订及应保留的行为。
```

任务正文默认沿用确认需求的语言，命令/ID/路径保持原样。将本片必需的准备、恢复和
独立验证交接写在本片三级标题内，或引用同版共享正文的具体条款及可定位入口；
不能把这些义务留在无引用的同级 TDD 章节。先核对执行身份、允许写入、场景准备者、
恢复者、验证消费者及实际调用能力；能力缺口写明影响与关闭点，不能靠增加说明闭合。

上述为交接要素，不强制逐段重复；简单任务可合并为紧凑段落或责任表。共用的验证
规则、状态说明及决定正文集中一次，任务保留适用 ID、本片例外与责任。

使用 execution_spec 时，每片正文必须放既有 `tasks[].body.human_review.module_spec_markdown`，
仅包含本片规格，不能复制整份 Plan（即使只有一个任务）。概览/旅程放
`shared.human_review.overview_markdown` / `journeys_markdown`；CLI 旅程同样写输入→输出/失败，
不虚构页面。共享条款集中一次，任务以具体 ID/入口引用；结构化字段不能替代本片阅读入口。
无该端口时用上述精确二级标题，三级及以下归本片，共享正文可放 `## Shared Spec`。
这是阅读约定，不改变身份/准入；未知、重复任务标题或仅摘要不能声明规格完整。
具名 GWT 正文维护在既有矩阵，正文引用 ID；必要摘录保持同义。路径、命令和生产者
来自 Task Map，原始证据保留 NOT_RUN/BLOCKED，不预填 PASS。

共享场景必须逐任务说明责任，例如 S-save-fail：功能任务的 AC-save 由局部命令
验证失败后旧状态与输入保留；装配任务的 AC-entry 由独立集成命令在正式入口验证。
实际 ID、owner 和命令来自当前合同。场景挂两任务不表示两片承担全部 AC；集成 AC
应说明如何覆盖业务条款。未找到直接关系标“责任待核对”，不能用同名 AC 猜测。

## 对最终工件做一致性审查

Planner 提交前与 Critic 判定前，执行[最终包对账](final-package-review.md)，在已有
评审工件中集中记录实际文件位置、发现和未覆盖项。执行一致性中的行为/权限/事务
细节按需展开，避免各份文档再次复制相同清单。所有必需来源和最终产物仍须核对。

复杂状态、幂等、序列化按风险补性质断言：前提、输入域、不变量、seed 和最小失败
输入。选择能区分正确与错误行为的反例；例如保存失败不能只查提示，要比较适用的
内存、DOM、持久化字节和用户输入。验证预期从来源推导，不从实现输出反推。
有限属性测试不是形式证明，也不强制外部服务、视觉及体验任务全部采用 PBT。

## 独立交接、返修和成本

Critic 读取同版来源及最终工件，不以作者自评或旧 approve 为答案。既有评审工件
分别记录规格充分性、一致性、可执行性、授权/未决边界和产品验证状态；给位置、
来源、反例、严重性及未覆盖范围，不凑问题数量。保留 finding 身份，记录修复、
有依据的驳回或未关闭原因；复用未变结论也要给版本依据，按配置返工上限收敛。

Critic 另核对接手者从本任务入口能否找到全部义务、来源语言是否保持、相同约束是否
已集中一次；区分产品 AC 与验证造父自身流程的协议，输入明确要求的治理 AC 仍须保留。
小需求优先少量完整切片，必需工件保留但避免重复叙述；不适用的设计活动说明理由。
同一来源未变且已经完整读到时引用既有证据，按影响展开所需正文，不重复整读全部
材料，也不跳过必需来源或配置要求的独立验证。缩短正文须保持责任链可读可取得。

做方法评估时读取[规格质量评估协议](spec-quality-evaluation.md)，冻结输入、模型、
权限和预算，保留合理正例、反例及失败。方法送达、真实生成、交接和产品验证分别
报告；浏览器回放不能冒充 Provider 生成，重复读取及 token 成本要实测。
