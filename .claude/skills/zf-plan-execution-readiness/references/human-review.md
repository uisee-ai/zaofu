# 面向人工审批的 Plan 与场景规格

适用于 Planner 生成和 Critic 审查。语义由 Agent 判断；UI 只投影同版工件，Kernel
只校验既有身份、摘要、分区及引用。无需新增任务 schema 或业务词汇 gate。

## 四层阅读顺序

1. 审批首页：用户/问题、交付目标、本期范围与非目标、条件扩展、阶段可演示结果、
   尚待决定的问题及其影响。说明本次批准的范围；批准 Plan 不等于关闭 Q 项或通过验收。
2. 模块规格：用户入口、字段/必填/枚举/派生来源、动作与权限、状态转换、正常和失败
   分支、关联资源、页面/表单以及精确来源。按独立业务行为展开，不以“实现原文全部”
   替代判据。不把未定选型、接口、阈值或条件扩展猜成已确定需求。
3. 业务旅程与验收：跨模块主流程、条件分支、修正/返工/失败后的状态；原子场景
   明确 Given/When/Then、既有 AC ID、验证命令 ID、来源条款和最早验证责任。
4. 工程附件：Task Map、依赖图、路径、命令、环境协议和评审历史。正文只保留本版
   决策结果与业务影响，详细 PC 返修时间线放附件，不掩盖未关闭问题。

首次阅读者应能回答“交付什么、怎么使用、异常怎样、如何验收、这次批准什么”。
保留原文和完整工程附件，不用 UI 折叠来删除需求或生成另一份业务真相。

## 既有 execution_spec 的作者约定

这是一种可选阅读表示约定，不是新的可派发 Task 合同。标准 PRD 新生成时应填写；
旧计划保持兼容，缺失明确显示为尚未细化。Task ID、AC ID、命令 ID 继续来自现有
Task Map/矩阵。所有内容与本次 accepted_plan 一起提交到同一个 Plan Package。
不把下列字段添加到 execution_spec 顶层，保持其 shared/tasks 分区合同：

```json
{
  "schema_version": "task-scoped-plan-input.v1",
  "shared": {
    "human_review": {
      "overview_markdown": "## 交付目标\n用户、范围、条件扩展与本次审批边界。",
      "journeys_markdown": "## 核心业务流程\n按用户动作描述正常、拒绝、修正与恢复。"
    }
  },
  "tasks": [{
    "task_id": "T-STOCK",
    "body": {
      "human_review": {
        "module_spec_markdown": "## 库存修正\n列出入口、字段、权限、状态及异常；引用来源和既有 AC。",
        "scenarios": [{
          "id": "SC-STOCK-DELTA",
          "title": "修正只结算差额",
          "source_refs": ["docs/prd/product.md#stock-correction"],
          "acceptance_ids": ["AC-STOCK-DELTA"],
          "command_ids": ["VC-STOCK-RUNTIME"],
          "given": "已记录消耗3件，当前可用库存10件，操作者具备修正权限。",
          "when": "将目标消耗改成5件，并使用同一幂等键重试同一请求。",
          "then": "首次库存变为8件、消耗变为5件；重试仍为8件且不新增扣减记录。"
        }]
      }

```

示例仅展示表达形式，不是任何项目需求。任务已有 body 字段必须保留；shared 的原有
安全、集成和跨模块义务不能移入仅 UI 可见的未绑定文件。无需在 prose 中自填 run/
revision/digest；由正式 Package 绑定身份。未启用 execution_spec 的路线可在既有
Plan Markdown 内采用同样阅读层次，不为版式强加新 runtime 端口。

## 条款覆盖与测试先行

- 页、表、场景的数量只能说明目录规模。建立 来源条款 → 独立可观察结果 → AC →
  实际生产任务 → 命令/场景 的映射；一个 AC 内的多条规则仍分别审查。保留已有 AC
  时可用多个场景细分，不因排版任意改派任务或改变用户批准的依赖边界。
- 字段级说明可以精确引用已确认来源，但必须能逐项导航，列出例外和未确认项；不能
  用“全部适用字段”掩盖未核查范围。来源冲突必须说明优先级与决策需求。
- Given 写实际主体、权限、资源/数量/状态；When 写真实动作；Then 写 UI/API/数据库
  可观察结果。覆盖正常、权限拒绝、边界、重复提交及相关故障原子性，避免每条套用
  相同空模板。事务多个断言保留一个原子动作，不为凑数量拆为部分提交。
- 每片先列具体测试用例，建立依赖和夹具，再记录有效行为 RED、实现 GREEN、必要
  重构及回归；缺依赖/启动失败不是功能 RED。业务测试与独立 Verify 的责任分开。
  Plan 只安排测试，不在规划阶段伪造 RED/GREEN、截图或产品通过。
- 决策沿用 task_map.owner_decision_items：问题、负责人/待指定、关闭证据、影响
  任务、最迟进入阶段；不把全部未决事项提升为全局阻塞。

## Critic 审查

阅读层来源/覆盖按照 `zf-plan-task-map-contract/references/review-ports.md` 绑定。
除逐项审语义外，从实际 Preview 输入检查端口名、摘要、来源全集和缺失项；
“文件已写好”不证明审批人能看到它，映射齐全也不证明产品测试已经运行。

除既有执行就绪审查外，逐模块核对来源与行为映射，抽查关键跨模块/权限/失败场景，
检查阅读层与 Task Map 是否同义。确认对当前任务的 AC/命令引用有效，场景能交给
独立 Verify 执行，非目标和条件扩展没有被扩大或删除。记录实际审查范围和未覆盖项。
源码字段未逐项核对时不能报“100%需求覆盖”。重复的 RED/GREEN 方法不算具体场景。
独立评审通过也不替代人类业务范围审批。已接纳产物只通过受控修订产生新版本，
不得覆写旧文件、修改摘要或绕过 Critic/人工批准。
