# 产品规格、技术设计与本批实施边界

Planner 生成规格、Critic 审查充分性时使用。SDD 指规格驱动开发；Plan 的 SDD
章节是其中的技术设计。原始需求 → 产品规格 → 设计决定与合同 → Task/验收，
不能根据 Task 标题反推用户意图。复用已有工件与精确引用，不要求固定文件名、
单独新增角色或把 Spec Kit 的模板复制成第二套状态机。

## 产品规格：让业务负责人可以独立审阅

- 从 authority 提取用户、问题、范围和非目标；保留条件能力及其启用决定。
  来源已有充分规格时精确引用并列出转换/例外；只有索引和“全部按原文”不算综合。
- 按用户价值组织故事：稳定标识、参与者与目标、优先级及理由、独立可演示结果、
  Given/When/Then、关联来源/既有 AC/Task。工程基础设施另列为必要支撑，
  不为了填表把网关、迁移 runner 等都冒充独立用户故事。
- 区分行为 AC、产品成功结果和工程命令。成功结果记录观察对象、测量方式、
  来源支持的判据/基线及责任人；不能凭空补响应时间、用户量或成功率。
  来源未给数值时保留定性约束并登记待决影响。上线后的业务 KPI 不是每条都要
  生成编码任务；验收所需测量能力有真实工程工作时才映射 Task。
- 一条旅程可以跨多个 Task，一条 Task 可支撑多个故事。优先级影响交付次序，
  不授权删除低优先级 mandatory 范围；阶段演示不代表完整产品通过。

## 技术设计：细化即将消费的合同

先写明本轮审查的模块、任务及当前依赖前沿。全局保留约束和剩余义务，
对即将实现或被并行消费者使用的合同展开以下适用项：

| 合同 | 需要明确的内容 |
| --- | --- |
| 架构与选择 | 实际入口、模块/外部系统责任、复用边界；重要决定、理由、适用限制及有意义的替代方案。既定 owner 选择直接引用，不为凑研究量重开决定 |
| 数据 | 实体字段、必填/空值/枚举/唯一性、关系、生命周期、数据真源；候选模型的采纳/调整及迁移、保留/删除责任 |
| 接口 | 生产者与消费者、稳定合同标识及版本或同版工件锚点、输入输出、校验、权限、错误及成功/边界样例；形式按 API/事件/CLI/模块接口选择 |
| 一致性 | 事务所有者及边界、锁/版本或竞争处理、幂等键作用域与冲突/重放结果、超时未知结果、失败恢复；不适用时说明原因 |
| UI/UX | 用户入口、动作与反馈、加载/空/错误/无权/冲突状态、适用的窄屏与键盘规则；原始效果图、已采纳设计、实现与视觉验收分开 |
| 非功能与验证 | 已确认的安全、性能、规模、恢复及观测要求；可复现的准备/命令/预期结果、验证责任及证据。规划阶段保留 NOT_RUN |

内容可以位于已有 Plan、规格分区或明确绑定的合同附件。相同合同只维护一个
权威正文，消费者携带同版引用及自身必要约束；不能只把它藏在未选读的兄弟任务。
已有候选 SQL/接口示意是设计输入，未经采纳不宣称已经成为正式实现合同。
UI 设计不要求每页都画高保真图，但必须覆盖实际适用的交互和状态。

对当前适用的项目原则/AGENTS 约束，记录设计前后的符合依据；有冲突则引用
具体原则、受影响决定及处理路径。缺少 constitution.md 本身不是失败，也不能
照搬其他项目的原则或忽略当前项目约束。

## 未决事项与并行

沿用现有 Decision Register，区分：

- 已授权、尚待任务落实的工程工作：在该任务提交/Verify 前证明；不要求待生成
  的锁文件、代码或测试收据先于负责创建它的任务存在。
- 当前消费者所需但尚未确定的合同：指明决定 owner、生产者、受影响 Task、
  最迟使用时点及关闭证据；消费者不能在协议未知时分别猜测实现。
- 后续/条件能力的决定：保留范围、触发条件及剩余验收；不阻塞无关前沿。

决定登记不是自动调度 gate。通过现有任务依赖、设计生产任务/任务内前置义务、
受控 replan 和相应验证责任落实顺序；写一条“使用前确认”不证明已被执行。
保留原登记的 `blocking` 值；`blocking:false` 不替代当前消费者的合同就绪检查。
发现两者有张力时，报告具体消费动作及缺证，交由受控修订落实依赖/责任；
不得由评审者直接改状态，也不能把它升级成全部任务共同阻塞。
尚无可执行合同的未来切片按已有 Epic 渐进细化方法保留，不铸造成空壳 Task。
若改变已接纳的合同/依赖/验收，提交新版本，经独立 Critic 与适用审批后生效。

例如：库存命令的公共幂等/事务协议由平台任务生产，作业与修正消费者只依赖
已采纳的接口。库存2、消耗3必须全体不变是行为判据；“后续补接口”不能证明
消费者已经就绪。与此同时，未知的未来报表统计窗口不阻塞无关健康入口实现。
上述数量仅为说明方法的样例，不得写成项目新需求。

## Critic：按实际证据分别裁决

把以下审查记录放入既有评审工件并绑定本次 Plan Package；不添加新的 runtime
verdict 枚举，也不把表格行数当 gate。每个维度写结论、精确正文位置、依据/
反例、影响任务、最小修订及关闭证据：

1. 产品规格：用户价值、优先级、边界和成功判据能否重建。
2. 设计充分性：当前前沿的适用合同是否确定且消费者可读。
3. 来源覆盖：来源 → 行为 → 实际生产者 → AC/命令是否语义成立；数据来源不等于
   展示或聚合的实现者。引用数量及关键词命中不证明覆盖。
4. 执行与验证：真实依赖、写入隔离、独立 Verify 和首个可运行反馈是否成立。
5. 未决与治理：决定的授权状态、责任/关闭时点、项目原则及未来范围是否保持。

明确本轮是全范围审查还是有界返修；有界审查引用所复用的同版/前版结论和未变
内容证据，不能把“启动修复通过”写成“全部产品规格和设计重新审过”。
实际未读/未评部分明确标记；不要用多个同义的“完整、ready、fulfilled”自证。
分开报告账本 `covered` 的分配声明、Critic 对该映射的语义核对，以及未来 Verify
的运行证据。看到 `covered` 不能推断后两者成立；发现错配给出具名返修，
不由阅读器或评审脚本直接改写账本。

`derived_plan_full` 是显式内容覆盖声明，不是测试通过、审批通过或所有任务
立即可派发。仅在声明范围的语义已审且剩余决定/未来义务明确时使用；尚缺
本次必须提供的规格时保留较弱内容声明并请求具名返修。正式 verdict 仍沿用
当前角色合同，绑定确切工件版本；结构检查和读收据不能替代语义判定。

## 方法验证

先验证真实角色拿到最新 Skill 及其引用，再用有来源的产品切片进行前向验证：
给评估者任务、方法和必要原始材料，不提供预期答案。检查其实际生成/评审是否
保留范围、识别未知公共合同、允许无关前沿继续，并指向具体证据。可加不同领域
样例检查可迁移性。记录输入版本、产物、审查范围和局限；样例通过不能推断
所有新 Plan 达标，方法/文档的字符串测试也不能替代这一证据。
