# 执行路线与任务切片

## 从实际路线开始

读取 briefing 中冻结的执行配置；已有项目可用
`zf plan inspect-execution --config zf.yaml --task-map <file> --flow-kind prd`
只读检查。已准入 Package 可附 `--plan-package <state-dir 内的 package 文件>`，
核对实际正文及输入体积。不得以另一个 profile 的能力解释当前路线。

- `task_verify` 是验收责任，不会创建派发阶段。阶段屏障通常在 Candidate 就绪后
  才独立 Verify；writer 自检不能描述成独立 Task Verify。
- 需要早期独立反馈时，选择有明确阶段出口的小批次，或评估显式启用已有 Task
  Pipeline 的适配与验证成本。v4 canary 不是默认升级，不自行更改在途 run。
- 写明首个可运行入口、首个独立反馈点、错误传播到哪些后继及如何返工。
  DAG 深度只描述依赖，不等于耗时；不能为了缩短数字删除真实前置。
- Plan 的安装命令不会自动接入 worktree：核对项目的
  `project.scripts.setup`、环境隔离、启动/健康检查和验证命令的真实消费者。
  在首个实现片形成锁文件后，以全新 worktree 验证初始化；缺依赖不是功能 RED。
- 对照 `impl_self_check_required`、实际输出协议与最终产品验收要求。
  区分 skill 方法要求和机械强制项；报告未接线项及解决责任，不伪报已执行。

## 先决定业务边界，再填写任务图

不要按每 N 条 AC、目录数量或角色数量分组。一个任务应说明可观察行为、
输入/后态、真实前置、测试及返工责任；同一原子事务包含多条 AC 是正常情况。
显式配置了数量上限时不能静默忽略：先检查是否能保持行为完整，必要时提出配置
调整，由已有受控配置/重新规划路径处理，不能靠把事务拆碎或合并 AC 文本绕门。

写范围唯一性继续有效。优先合并紧密修改同一领域的工作、指定共享协议 owner，
或分批演进；不要为了凑互斥路径发明大量 part-* 插件和临时抽象。

| 场景 | 合理边界及反例 |
| --- | --- |
| 库存转移同时扣源库、增目标库、更新流水 | 同一事务 owner；片内分步验证。不把三次写拆成三个可独立成功任务 |
| 文档发布与全文检索 | 发布先形成可运行路径；索引任务依赖已发布事件协议，而不是等待全部编辑功能 |
| 数据导入与格式扩展 | 最小获准格式先跑通登记、读取、错误展示；其余格式按真实解析依赖扩展 |

## SDD/TDD 的细化时点

简单任务不额外创建设计 agent。高风险事务、权限、恢复及共享接口需要短小规格：
具体实体/状态、API/事件/插件字段、版本兼容、逐写失败后态和黄金反例。
共享协议先以最小版本实现并证明调用者接线，后续业务细节按片细化。

复杂任务的片内步骤绑定具名用例，记录可复现的实现前基线、测试补丁、有效失败、
实现后版本和通过收据。不能把多条业务断言装入一段通用 RED/GREEN 文案就声称
TDD 已执行。Verify 检查关键证据，环境失败与产品失败分开。

## 输入与最终验收

完整权威规格保留；任务输入应是显式范围，不是模型临时摘要。
大型补充行为规格可使用 task-map contract 中的 `task-scoped-plan-input.v1`：
共享规则 + 每任务完整正文，来源和决定引用仍同版；全局 Candidate 继续读取全量。
不要套在已有固定 schema 的矩阵外面，也不能用它隐藏其他任务真正需要的接口。
未分区的旧端口保持全文。Task Map 本身保持调度契约，避免重复内嵌整个测试正文。

评审记录至少解释：切片理由、依赖理由、独立反馈时点、输入充分性和未验证边界。
评价改进用首次可运行/独立反馈距离、实际读取量、依赖等待和返工范围；
结构变小不自动等于语义更好。保留最终全量 mandatory 验收，不沿用阶段排除项。
