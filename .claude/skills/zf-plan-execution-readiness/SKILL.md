# Plan Execution Readiness

本方法用于把完整需求转换为可执行计划。它不定义新的 task schema，不写运行态，
不替代 Kernel 的引用、路径、代际及完成证据检查。产物使用现有 Plan、task_map、
矩阵和 Critic verdict；项目语义判断必须附来源，不能变成 Runtime 的项目规则。

先读取 `zf-requirement-reconciliation` 核对来源及未决问题。大需求、未来范围尚待
细化或需要调整依赖图时，按[薄 Epic 与渐进细化](references/epic-refinement.md)
保留全局义务并形成当前执行边界；不把 Epic 规划状态写成 Kernel Task 状态。

阻塞假设只能通过实验回答时，读取[有界 Spike](references/bounded-spike.md)，
明确停止条件和等待其证据的后继；已有权威证据足够时直接引用。

规划长依赖链、并行实现或新项目冷启动时，先按
[执行路线与任务切片](references/execution-route.md)核对有效配置和反馈时点。
Critic 收到 `plan-execution-review` 必需输入时逐项解释其事实与本计划的匹配关系；
该报告没有语义 verdict，不能把机械 preflight passed 当成实施就绪。
将其中 `input_binding` 的 Task Map／有效策略摘要、revision／generation 与本次产物
一并引用到既有评审工件；`capacity` 只报告配置实例、依赖层宽度和写入范围检查，
不代表实时空闲容量，也不授权新增 lane。提出配置差异时逐项给出旧值、候选值、
来源和受影响任务；输入摘要或代际改变后重新复核，不沿用旧评审的适配结论。
收到 `usage_observations`、预算失败或需要提出预算修订时，按
[实际计量方法](references/usage-budget.md)复核，
区分新增 token、缓存、重试归属和未知费用，不从输入字节数推导模型成本。

Planner 在提交最终工件前、Critic 在决定 verdict 前，读取并执行
[执行一致性复核](references/execution-consistency.md)。它检查实际动作生产者、
状态相关权限、本片/候选验证边界、完整修正事务与跨工件决定版本；结果记录到已有
评审工件。方法加载或结构检查通过不代表这些语义检查已经通过。

来源、决定或合同发生变化时，按[规格修订与审查影响](references/spec-revision-review.md)
记录新旧版本、受影响消费者、重审与复用依据；摘要写入现有 Plan 人读正文。
交付可运行产品或部署环境时，按[可复现交付规划](references/delivery-validation.md)
明确指南、环境与关键旅程的生产者、独立验证责任和执行时点。

## 条款与验收责任

规划阶段先区分“现在必须取得的证据”和“未来阶段必须执行的门禁”。例如独立Critic、
Plan批准、Verify/Judge和最终交付尚未发生，应在计划中保留责任人、触发条件、阻塞边界
与验收方法；不要为了证明它们已发生而遍历事件账本，也不能删除这些必需验收。
briefing中的 `Compiled planning execution facts` 是当前已加载配置的事实，包含策略摘要、
阶段、writer配置、Plan批准要求和task pipeline；它不代表语义质量或执行授权。
已有事实能回答的问题不再重复探测全量CLI帮助或编译输出；遇到缺失/冲突时只查询精确问题。

完整阅读必需来源并核对已持久化的read receipts。首读输出截断时只补齐缺失部分，
不要反复整读同一批技能、长报告或事件列表。独立来源可成批读取，但必须逐项检查结果，
不得以批量调用成功代替内容已读。需求、扫描和合同具备后先形成完整工件，再按预校验的
具体错误有界修正；工具探索、重复读取和“等待未来批准”均会消耗Operation预算。

先读当前需求 authority，再对每个 AC 内部的条款审查，不能只统计顶层 AC。
每条应能定位：来源 → 可观察结果 → 行为生产者 → 验证 owner/tier/command →
最早可验证阶段。输入、状态变化、拒绝条件、失败后的观察结果不明确时补规格。
“该章节全部实现”可以作范围索引，不能替代可执行判据。

- 工程盘点、架构决定、环境确认用相应静态/契约验证，不强制生成 UI 旅程。
- 事务回滚、同幂等键不同请求、权限拒绝、删除保存等是运行行为，不能仅由盘点
  文件或接口枚举证明。将行为条款绑定到真正拥有实现和测试的切片。
- 一个 AC 混合前置决定和运行行为时拆开验收责任，保留原需求映射；不以任务名、
  prerequisite 标签、空 journey_ids 豁免整个章节。
- `task_verify` 的局部结果只能依赖本片及已完成前置行为。跨后续切片的结果可以
  保留为 mandatory `candidate_verify`，必须有明确后续生产者和验证时点。
- 条件扩展保留来源、启用决定和未启用范围；只在进入受影响阶段前关闭阻塞决定。
  不为开始工程盘点提前猜测所有产品决定，不把未启用条件写成产品已通过。

## 人工审阅与具体场景

生成或评审 PRD／技术设计时，先按[规格与设计就绪](references/spec-design-readiness.md)
区分产品故事、设计合同、当前实施前沿和未来决定；Critic 分项记录证据与审查范围。

提交或评审 Plan 前，按[人工审阅方法](references/human-review.md)组织审批首页、
模块规格、业务旅程与原子验收场景。阅读层绑定同一 Plan Package，不创建第二任务合同；
旧计划缺少场景时如实报告，不把工程命令或通用 RED/GREEN 模板当作充分规格。
## 领域与模块覆盖复核

对大型需求或多份 authority，先建立来源单元到计划语义的覆盖账本，再审任务图。
账本使用已有矩阵或评审工件，不新增 canonical task schema。按来源实际内容分类为
产品目标/范围、领域/模块/能力、用户旅程/行为规则、数据/API/事件合同、状态与错误、
权限/安全、集成与非功能约束、验收/测试/E2E 义务；没有某类内容时记录“来源未定义”
及分组理由。

每个来源单元必须标记 `covered`、`explicit_non_goal`、`pending_decision` 或
`out_of_scope`，并保留稳定 section/heading anchor、语义陈述、Plan 位置、需求/AC、
任务、测试/命令、证据和责任阶段。`covered` 必须同时具备可观察行为或明确合同、实际
生产者和可成立的验证断言；其余状态必须有原因和影响范围。章节级 ref 可以作为索引，
不能单独证明整章的每条业务规则。任务数、标题、关键词命中和矩阵行数都不能替代这
项复核。

若 mandatory 来源单元没有归类、没有语义 Plan 正文、没有 producer 或没有验证路径，
Plan 不能声明完整；Critic 应指出具体 source anchor、模块/能力、最小修订和验证责任。

## 切片与阶段集成

每片在 Plan 中回答：完成后可演示什么、通过哪个实际入口、依赖哪些已完成行为、
失败后应重做哪一片。模块名、路径项数和 AC 数量不是单独的大小判据。

1. 把一个模块中的独立用户行为分别评估；共享基础契约先建立最小版本，业务契约
   随行为细化。不要先冻结全站全部接口才产生第一条可运行路径。
2. 明确启动/接线所有者，并尽早交付可运行入口。可用稳定的扩展注册协议和各片
   独占注册文件；必须证明真实调用者会加载它们，不新增没有调用者的库。
3. 中间阶段交付读取闭环、状态变化闭环等可观察结果；最终装配负责全量验证。
   不只把原阶段名称放进最终任务，同时把所有集成反馈推到最后。
4. 全图仍遵守写入路径唯一性。多个阶段不能声明同一入口文件的独占所有权，
   即使波次不同；阶段验证任务只拥有自己的 spec/runner/evidence 路径。
5. 单次事务中的多项状态变化保留单一命令所有者，用片内 TDD 验证正常、失败
   回滚、修正和幂等；不能拆成对外可见的部分提交来凑小任务。
6. 只读既有状态与启用新的变更命令分开分析。依赖必须来自实际调用、数据或
   证据生产关系；不因为名字相似或流程图排列就添加依赖。
7. 尊重 owner 明定的任务图。owner 已授权重设计时可以修改受影响 ID、依赖、
   AC 和路径，保留旧新映射及理由；不能以“保持原任务图”阻止已授权修复。

## 正例与反例

| 输入 | 判定与理由 | 修订与可验证结果 |
| --- | --- | --- |
| “记录数据库版本与事务重试策略”由盘点任务生成决定文件 | 合理前置决定；文件可证明决定已记录 | 保留盘点 AC；运行时重试另外由命令切片负责 |
| “同 key 不同请求拒绝，失败回滚”也用 inventory.json 的键存在证明 | 拒绝；文件存在不能证明请求冲突和回滚 | 分别绑定请求冲突与数据库事务测试；保留原条款来源 |
| 一个车辆模块同时有基础读写、保险资料、跨项目调拨 | 多种独立行为，应说明拆分依据 | 分为可演示行为片；调拨保留原子事务所有者 |
| 一次作业必须同时改变库存、设备和流程 | 可保持一个原子命令片 | 片内逐项 RED/GREEN：正常、失败无部分写入、重复请求不重复执行 |
| 首片只能导出函数，第 13 波才接入口 | 集成反馈过晚 | 先有调用者和最小路径，后续行为通过独占扩展文件接入并按阶段验证 |
| 已取消状态只读必须等物理删除功能完成 | 缺乏真实依赖依据 | 只读断言归已有流程片，新取消命令按条件决定另行规划 |

Critic 对正例应说明为何可接受，对反例指出具体条款/任务、来源和最小修订。
计数、关键词匹配或机械预检全绿不能替代上述语义判断。

## 提交前证据

- Task Map 形成后复核初始执行建议：任务依赖、owned paths、共享入口、实施容量和
  独立验证责任是否匹配已批准的有效 profile。并发以真实独立性为依据，不按任务数量扩容。
- 原配置可承接时继续，不增加无意义的配置变更或批准；若需要改变冻结策略、预算、
  权限或拓扑，在现有 Plan 评审证据中说明缺口、保留当前 generation，并请求受控修订。
  不直接修改运行中 YAML，不通过重新 classify 静默换图，也不降低原 PRD 的验收范围。

- Plan 保留条款责任、切片结果、集成时点、条件决定及主要反例审查结论。
- task_map 与矩阵 ID/路径/命令保持一致；每项缺口有明确 owner 和 done_when。
- 完整 Plan、矩阵和来源索引通过正式产物引用交接，摘要仅作导读。
- 人工审批入口必须能从绑定产物重建 PRD/SDD/TDD/Decision Register：
  SDD 不能只有任务标题或 source excerpt，TDD 不能只有命令名；每个
  acceptance 至少要有预期结果、验证命令、owner/tier、证据路径和判定规则。
- `derived_plan_full` 还必须能从绑定产物重建上述领域/模块覆盖账本；每个来源单元的
  disposition、语义正文和影响范围都要可读。不能用“章节已覆盖”替代模块/能力级复核。
- Decision Register 必须与 Plan 正文和审批 payload 使用同一组稳定 id；缺失、
  重复或只存在于 Markdown 的决定记录为一致性缺口，不能让摘要显示“无决定”。
- 由独立 Critic 复核，不自批 Plan；实现前没有运行证据是正常计划状态。

验证本方法时，既验证 Planner/Critic 依赖物化，也记录真实样例的语义评审。
物化测试通过只证明方法可读，不能证明任意生成计划都满足这些规则。

## 来源分类与规格充分性

先把来源记录分类，再决定验收方法。使用现有矩阵或独立评审工件记录，不新建
canonical task schema，也不把语义分类硬编码进 Kernel：

| 类型 | 它证明什么 | 必须补充什么 |
| --- | --- | --- |
| 来源事实/历史说明/标题 | 背景与追溯 | 来源、适用范围；不冒充运行测试或计入行为通过率 |
| 决定/外部前置 | 某阶段需要取得什么确定信息 | 逻辑责任人、受影响任务、进入阶段、关闭证据、未关闭时允许/禁止的工作 |
| 行为规格 | 用户或系统的可观察约束 | 输入、前态、动作、预期后态/拒绝及失败不变集；关联实际行为生产者 |
| 验收用例 | 如何证伪上述约束 | 具名断言、测试层级、样本/边界、命令与证据责任 |

原文复制、test 名称或 cases.json 路径只证明有追溯；是否足以验收需要逐项判断。
独立入口分别审查容器、成员及字段边界，不能用CLI的顶层校验证明可单独调用的
业务函数也已校验。已提供的冻结外部验收逐项映射到Plan及反例；缺少非法输入行为
约定时明确该限制或形成决定项，不擅自编造异常类型，也不以当前自带测试全绿替代核对。
不按“复制比例”判失败，也不强制为标题或历史说明制造输入/后态。
已知的高风险行为（鉴权、复合写入、并发、资金/库存、删除保存、恢复）在 Plan
阶段就应有具体断言。只有依赖未决接口细节的参数可以延后；逐项记录延后内容、
生产者、最迟细化阶段及 Verify 如何核对。不得用“实施时完善”整体转移规格责任。

出现跨页面/模块的全局承诺、资源职责或跨域权限时，读取
[跨域义务](references/cross-domain-obligations.md)，按覆盖范围和真实行为生产者分配验收。

## 反例审查与返工复核

Critic 对每个高风险 AC、跨域义务及本次修改的映射提出：
**是否存在满足此 AC，却违反原条款的实现？**
记录具体反例或排除理由、来源、受影响任务、最小修改和验证标准。
例如仅实现项目字段仍可通过局部 AC，却没有其他页面接口，是有效反例；
“可能不完整”而无失败场景不是充分的拒绝理由。

返工复核有两份边界，必须同时说明：

1. 本次 fix_items 是否修复，旧已验证约束是否保持；
2. 当前完整 Plan 的审查维度、已读证据、反例、未覆盖内容和剩余风险。

不能因为已列修复全部关闭，就称其余问题只剩 Q 项。旧批准、结构计数、检查项数量
均不能替代本轮语义证据。未覆盖范围明确登记；若影响当前可执行性，给出具体返工；
若仅依赖真实外部决定，保留阶段阻塞而不循环要求 Planner 编造答案。
Approve 表示本次声明的规划审查通过，不认证未来测试已执行或产品已交付。

证据引用只指向实际可解析的产物或事件。CLI返回的stdout不是持久JSON文件；
未保存输出时，不将工具名或拟定文件名写成 `evidence_refs`。引用已读取的不可变
输入及实际工具收据，并在审查正文说明判断与限制；若必须保存审查输出，使用本次
派发允许的产物路径并确认文件存在，再引用其ref/digest。不能用虚构路径填补证据。
## 人工反馈与版本复核

Preview 评论必须落到当前 Plan revision 及 source anchor、requirement/AC、decision
或 Plan section。Replan 时比较旧/新覆盖账本、SDD/TDD、决定、task map、依赖和证据，
明确哪些内容保持不变、哪些任务需要返工、哪些已完成任务可以复用。影响范围、合同、
owner、依赖或验收的修改会使旧 approval 失效；未受影响的完成证据可以保留，但不能
把旧 verdict 当作新版本的 Critic 结论。

## 片内执行与最早反馈

高复杂度片、UI 切片或包含多阶段 smoke/candidate 验收时，读取
[最早反馈](references/early-feedback.md)，列出片内步骤及各阶段可运行入口。
首个独立反馈点由当前路线决定，不把全部验收默认推到最后。

Q 项允许 named owner 待指定，禁止猜测真人或替 owner 作产品决定；同时明确
责任角色/任务、最迟关闭阶段、关闭所需证据和受影响执行边界。未知前置不影响
无依赖的盘点，但不能据此宣告依赖该前置的实现已就绪。

## 正反例校准与阻断依据

仓库 `tests/fixtures/plan-counterexamples/cases.json` 提供有来源的合理计划及变体。
先接受合理正例，再逐项指出反例的来源要求、具体任务、可观察失败与最小修订。
Kernel 报告未映射 claim 是诊断，不等于已验证覆盖；有映射也不能证明语义完整。
只有可追溯的要求遗漏、反例或不可执行条件才阻断，命名与个人偏好作为非阻断建议。
不重复已完成的机械校验，不要求计划期提供实现后才产生的测试或截图；检查其生产方法。
语义对照需独立 Critic 的实际输出，fixture 标签与模拟答复本身不构成评测通过。
