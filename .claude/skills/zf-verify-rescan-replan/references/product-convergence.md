# 对照意图收口产品

Discovery/rescan 使用已绑定的原始需求、当前批准规格/设计/Task 与固定集成候选。
代码提供实现证据，不能自动成为新需求。任务已 done 或所有分片 Verify 已通过，
仍需核查当前产品目标；旧结果只在目标、责任及证据仍适用时复用。

## 双向核对

从每项 mandatory 行为/验收/设计义务找到实际生产者和证据，再从本次候选的相关
变更检查是否有冲突或需要解释的新增行为。限定在声明的交付范围，不对整个仓库
无关代码重新立项。必要工程支撑可以由批准设计/合同解释，不强求每行代码都有
独立业务需求；未经确认的新增能力先交由有权者判断，不直接删除。

在既有 gap_findings/审查正文中按需标记以下语义类别。它们不是新的 runtime
gap_category/verdict 枚举；正式提交仍遵守当前 briefing 的输出协议。

| 分类 | 何时成立 | 需要的证据 |
| --- | --- | --- |
| missing | 规定的行为或交付物未实现 | 来源、预期入口、已检查范围及缺失证据 |
| partial | 只满足部分规定场景 | 已成立与未成立的断言、边界和执行证据 |
| contradicts | 当前行为与批准意图相反 | 具名条款、实际结果及可复现反例 |
| unrequested | 相关新增行为没有可找到的授权依据 | 实际增量、已核对来源、需要解释/决定的范围 |

分类按具名断言选主类；同一行为可关联多个条款，但不因分类重叠重复生成修复任务。
以实际反例、影响及最小修复为准，不要求类别互斥到掩盖行为事实。

为每项记录稳定 finding ID、source/AC/Task、候选身份、精确证据、严重度、受影响
范围及最小修复。未读、未跑、环境失败不自动归为 missing/contradicts；明确 unknown
或阻塞原因，交给当前协议的允许 verdict，不发明新的运行态。没有证据不能声称
没有缺口；已证明错误也不能仅因其他测试通过而消失。

检查已有 corrective task 链的最终行为，不要求恢复被合法替代的实现细节。
保留仍有效的已完成工作，通过既有 gap plan/replan 提交最小增量；不降低 mandatory
要求、不重编号历史任务、不直接改 TaskStore/冻结工件，不重复铸造等价待决方案。
新目标改变则需要相应授权和受控版本，不能沿用旧通过结论。

## 独立重现交付指南

交付范围要求可运行产品时，从受控输入定位同版运行指南和正式命令/AC，确认目标
候选及外部环境授权。独立验证准备、启动、初始化、测试身份、关键旅程及清理步骤，
按合同核查持久化/恢复。可以复用 current 的合格收据，但须指出复用范围和依据。
不能依赖作者未声明的手工操作、共享服务状态或聊天中的秘密配置。

指南缺少必要步骤时点名缺口；外部条件不可用时保留阻塞和未验范围。入口健康、
文档检查或 mock 成功不能替代要求的实际产品行为。只清理本次自有资源。
库或文档交付按实际入口验证，不强制容器化，也不把验证者变成部署文件的实现者。
受命诊断时可以提供指南修订草案；草案自检不代替交付 owner 的正式产物，也不
形成另一位验证者的独立验收。最终候选仍按原合同取得有效证据。

收口报告分别说明已审范围、四类有证据的问题、未验/阻塞项和仍须交付的义务。
只有声明范围中的 mandatory 断言都有 current 证据时，才能给出相应无缺口结论；
最终 Thin Judge 继续消费已准入结果，不承担补测或补造规格的责任。
