# 项目验证方法

Skill 固化方法，项目 Skill 提供实际入口，Prompt 指定本轮目标，测试代码执行断言。
本方法用于 ZaoFu 自身和由 ZaoFu 开发的产品；沿用当前合同与结果 profile。

## 先确定验收对象

记录候选 commit/ref、base、任务/Run/attempt（若有）、合同版本及验收责任。
只承担当前阶段负责的条款。普通交互会话不创建任务身份或发送完成事件。
若检查含未提交改动，记录 diff 摘要并标为工作区探测，不能签收为纯 commit 证据。
按照已有授权执行；选择真实 Provider、部署环境或外部写入前核对本轮范围。

审查变更时，以实际产物核对作者描述。获准读取 Git 的角色同时检查 status、未暂存与
已暂存 diff，并逐项审查 scope 内的 untracked 文件；已提交变更按本次固定 base/target
比较。工作树测试不能证明不同内容的 index/commit。只读 Reader 沿获准的 artifact/source
入口核对相同信息，不因本方法扩张读取或执行权限；输入缺失明确列为未验证。

从原始需求和当前合同开始列地图，再用路由、代码和现有测试补充。未实现的需求
仍保留为缺口，不因没有页面或测试而消失。条款的独立预期不能从候选输出反推。

| 条款 ID/来源 | 当前验收责任 | 场景与初始状态 | 预期/断言 | 命令或用例 | 方法/外部边界 | 本轮结果与证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 使用合同已有 ID | task/candidate/human 等原值 | 输入、动作、故障点 | 可观察的结果和副作用 | 精确可运行入口 | mock/API/浏览器/真实 Provider | 未执行/通过/失败/阻塞及 refs |

这张表是方法产物，不是新任务 schema；其“未执行”等状态不直接替换 runtime verdict。
“已有测试”和“本轮运行通过”分别记录。只映射适用的正常、拒绝、恢复、并发和隔离场景，
不强制每个功能套用所有维度。环境错误或缺证据不能计入产品通过/产品失败。

每项行为写明真实触发入口及必要前置：用户从何处进入，或哪个公共 API、CLI、库调用、
事件消费者触发它。直接访问内部地址、绕过实际调用者或仅测 mock，不能证明入口接线。
单元测试仍可证明其公共边界内的规则，不因此强制全部改成浏览器或端到端测试。
局部修复沿实际影响选择一个可能退化的相邻行为，核对原预期和当前证据；确无相邻影响
时说明边界，不人为增加场景，也不因新增本方法重跑仍有效且获准复用的收据。

## 项目方法提供什么

先读现有项目方法，再补必要信息，避免为同一项目建立多个相互矛盾的验证入口。
项目源码规则决定 Skill 的位置与分发方式。项目方法应写明：

- 启动命令、就绪信号、依赖、授权账号及最小无模型 smoke。
- 测试入口与功能地图；API、CLI、库、批处理同样使用其适用的验证工具。
- fixture 初始化和重置、数据版本/摘要、预期结果来源。
- 并发资源的隔离单位：端口、工作目录、账号、数据库/schema 或租户。
- 命令、退出码、截图、接口响应及实际副作用的证据位置。
- 失败重现和清理方法：只清理本次创建的资源，保留验收证据。

对于使用 PostgreSQL 的数据产品，可用项目已有 Compose 启动依赖；每个并发验证
实例分配独立数据空间。导入/处理/导出同时检查 API、持久化记录和输出内容。
使用项目 dataset 时保存摘要；补充公开数据时固定来源与版本，标明合成或外部样本。
本方法不为所有项目强制安装数据库，也不把某个产品的目录写入通用 runtime。

## 选择执行与断言

- 使用现有测试和影响闭包；新增断言覆盖实际缺口。API/数据库/文件可以精确判断时，
  用确定性检查；视觉操作与语义判断补充画布、图表、反馈和可用性场景。
- Playwright、Midscene、e2e 都是可选执行器。保留项目已有 runner；需要视觉能力时
  加适配层，不因加载本方法就安装工具、迁移套件或修改控制平面。
- 执行者完成操作后，从新的观察和原始条款验收；不以执行者总结代替结果。
  AI 判断证据不足时保留不确定性。不同模型或 session 本身不能证明判断独立。
- 可缓存动作或复用符合当前合同绑定条件的命令回执；记录 live/replay 和模型来源。
  缓存命中、重新派发、HTTP 202、页面显示完成，都不单独证明本轮交付符合要求。
- 恢复场景检查取消/失效、旧操作结束或隔离、新执行、结果准入和最终产物。
  区分运行时重建、OS 进程重启、真实 Provider 三层，不把分段测试拼称一次真实闭环。
- 并发用例证明至少两个符合调度条件的任务同时在途，再检查独立产物与汇总；
  顺序完成两个任务不能证明并发，存在合法依赖时等待也可能是正确结果。

## 检查测试是否有效

对新验收方法使用小型反例：错误内容、缺失记录、重复副作用、陈旧 target 等。
在隔离 fixture 或独立候选中植入指定错误，要求断言因该错误失败。
命令不存在、模型不可用、无关超时不算检出产品缺陷。修复后用同一断言复测。
探索发现先独立复现，再作为缺陷报告；未复现、环境限制和产品缺陷分别记录。

## 证据与结果

记录实际执行命令、cwd、退出码、候选 commit、配置/数据摘要、用例 ID、执行层级，
以及适用的 Run/attempt/generation 和附件 refs。结果绑定所测对象，避免混入其他轮次。
ZaoFu worker 继续使用当前 briefing 的证据写入和 `result` 提交路径；大正文持久化
并绑定摘要，不另创 verification schema，不直接改 ledger、TaskStore 或终态。
普通维护会话保存命令日志和报告即可，不虚构 worker 回执。

输出覆盖表、实际结果、未覆盖项和下一责任方；分清问题属于产品、验证器还是环境。
没有发现阻断问题时，写出实际检查过的条款、入口、版本与证据，不以“零 finding”代替
覆盖说明。末尾保留“未验证项”：逐项列条款/行为、未执行或证据不适用的原因、影响及
下一责任方；确无遗漏时写明本次范围内无未验证项。该段放入既有报告正文/summary，
不扩展严格结果 schema，不把未到阶段的后置验收变成当前阻塞或将 mandatory 缺口判绿。
下一次运行可能覆盖 runner 的默认输出，因此需要保留的证据使用独立目录。
结束时清理自己创建的进程、容器和测试数据，证据不随临时环境删除。
