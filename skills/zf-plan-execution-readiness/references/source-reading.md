# 完整来源的读取方法

用于长 PRD、多端口 Plan 和返工包。目标是每项语义读到、重复包装少读，
不改变来源 authority、必读清单、读取凭证或最终审查范围。

1. 先定位，再展开。读取 manifest、工件引用及必需方法；用现有工具查看文件大小、
   JSON 顶层类型/键和列表长度、Markdown 标题及行号。不要先 `cat` 所有大文件。
   按实际类型访问字段，不猜测 JSON 是 dict 还是 list。目录和计数只用于导航。
2. 每类内容选择一个完整的同版正文来读。包装中的 `control_result`、`plan_ports`
   与独立工件可能重复；先校验引用摘要或解析后的完整值相等，才复用已读内容。
   相同名称、ID 或条数不证明相等；有差异必须读差异并查明当前 authority。
   必读来源仍通过本轮指定读取渠道履行凭证，不以本地哈希代替 read ledger。
3. 一次建立完整索引：全部任务/AC、依赖、命令 owner/tier、决定和源条款位置。
   然后分块读取每个任务的完整行为、验收和 TDD 正文，对照对应原需求段落及共享
   规则。不能只读首项或关键词命中的片段；原需求中没有任务映射的条款也必须核对。
   索引不是压缩后的规格，也不能替代正文。
4. 合并同一审查问题的独立读取。例如并列显示某 AC 的来源原文、任务断言和矩阵
   责任，减少为一个关联往返多个工具调用。保留来源路径、JSON 路径或行号，
   不反复重印已读的共享规则、完整登记表或全部包装。
5. 输出要能读完整。按工具容量选择块大小，出现截断时缩小范围并续读遗漏部分；
   不用 `[:N]`、`head` 或固定抽样假装完成完整审查。未显示的原文仍留在源工件中。
6. 在已有评审工件中记录已核对的范围、引用和未覆盖部分。发现阻断问题可以报告
   rework，但仍须明确其余范围是否完成；不得把提前结束的便宜运行算成同质量改进。

评估使用相同来源、任务和模型，连同全部失败记录比较实际 usage 与耗时。
输出字符数、文件体积及 digest 相等都不能证明模型节省 token 或语义审查通过。
