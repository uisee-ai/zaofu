# 按需审查与有界返修

先读本次批准的 `plan_review`、focus 和实际必读清单。none 不派 Plan Critic，Planner
提交完整产物并自检，不能声称独立通过。targeted 是授权范围内的独立审查，full 是
完整规划审查；策略来自批准配置，作者不得自行免审。通用质量方法按本次范围适用，
不能把 targeted 又解释为每个维度、每个附录全部必读。

## 首次定向

原始需求、共享约束、完整 Plan、Task Map、来源索引和执行事实先形成全局背景。
必读清单之外的补充矩阵仍在 manifest 中；按 focus 沿来源 ID → Task → AC →
验证 owner/tier/command → 最早可执行阶段读取相关原文，缺少上下文或出现跨范围
矛盾时受控展开。不得只信作者摘要、文件名或“已覆盖”的计数。

在现有 verdict 的 summary/evidence_refs 简短记录每个 focus 的证据、具体反例或
排除理由、实际审阅范围、未审范围和扩读。定向 approve 不表示全文通过；若不能
完成指定问题的审查，报告未完成或具体返修，不以省 token 为由批准。

`plan_content_profile` 描述文档完整度，不描述 Critic 覆盖范围。完整 Plan 可以只接受
定向审查；不可因 targeted 就把作者同版 `derived_plan_full` 降为 `derived_plan`。
评审范围写入 summary/未审范围；`summary_only` 只用于有原文证据的缩略文档。
命令转义疑点先解析绑定的原始 JSON 并做最小语法核验，不能把显示层转义当成缺陷。

首次 targeted 没有历史全文基线是正常情况。只有声称继承历史审查时，才必须核对
同版摘要、已验证覆盖及新上下文适用性。输入策略中的 targeted_navigation 不等于
历史 incremental；失效或不完整历史不能当成新版本的完整审批。

## 阶段职责与返修

Channel 核对需求、业务边界、歧义及异常验收；Plan 核对新增设计、任务依赖和执行
责任。已确认 PRD 的同版记录提供来源基线，仍需检查 Plan 新增或改变了什么；不
把 PRD 签署直接当成 Plan 通过，也不重写一份相同的 PRD 评审报告。

返修先列原 fix_items 的状态：已解决、仍存在、有反证不成立。对每项定位当前原文、
改动及关联责任；随后检查变化影响的共享约束和依赖。禁止仅凭作者“已修复”关闭，
也不重复已排除的问题、不为措辞偏好不断添加阻断项。发现同类缺陷时一次指出完整
影响范围，让作者修复这一类问题。沿用既有回合预算；达到上限或阅读执行失败时
报告确切边界，不自动通过，不把 reader 未完成一概解释为 Provider/基础设施损坏。

## 具体反例

- T-CORE 只有共享函数，却把“HTTP 400 与 CLI 非零退出”列为本片 mandatory AC；
  本片函数测试通过不能证明该 AC。把本片行为与后续两入口集成责任分开，保留原义。
- T-CLI 和 T-HTTP 是兄弟任务；T-CLI 的 task_verify 不能要求尚未存在的 HTTP。
  仅说明未来命令“不阻塞”无法修复已有 AC 的完整语句与 owner 矛盾。
- 各片要提供独立用法/验证，正文提到了用法，但真正的手工验收命令只归最终装配：
  检查当前片实际选中的命令，补齐各片责任；不要强制每片写同一个 README。
- 审查输入中一条 SCENARIO 包含其他场景与附录：核对原文边界和映射，不能只看
  Scenario 计数或重复复制的一长段“来源文本”就称追溯完整。

## 作者的场景抽取自检

脚本提取 Markdown 时，标题块在下一个同级或更高层级标题处结束；较深标题仍属于
当前块，代码围栏中的 `#` 不当标题。不得使用只能匹配固定空行数或漏掉同级标题的
正则，把文末后缀归给首场景。若不确定，直接按原文标题/行范围导航，不发明抽取结果。
保存后独立抽查首、中、末场景及最后场景与附录的边界，每个来源 ID 对应其真实语义。
索引保留精确定位与简短说明，正文在唯一权威位置；不在每个矩阵重复粘贴整份 PRD。
