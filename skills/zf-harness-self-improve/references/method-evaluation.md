# 方法贡献与成本对照

先定义本次改进要影响的行为和固定案例，再改方法。案例用原始请求的自然表述，
评分标准放在 project/ 之外，不在 prompt 中透露预期错误。保留正例和近似反例。

复用 `scripts/eval-plan-execution.py`：baseline/candidate 是冻结 Git 方法包；
`--variant` 仅在隔离副本覆盖指定的既有方法文本；`--include-bare` 增加无方法组。
裸组输入必须自包含，不能强制要求读取只存在于方法组的文件。所有组权限和事实相同；
减少方法不减少容器隔离、安全或任务约束。每次显式限制调用数、重复次数和超时。
`--prepare-only` 不调用 Provider/Docker，只证明输入分组，不算真实评估。

用 `scripts/eval-method-report.py export` 生成匿名编号答复/轨迹和评分模板，
只把 review/ 交给评分者，映射与指标留给操作者。内容仍可能泄露版本，故只能声称
隐藏了组别标签。检查实际输入、工具调用和最终答复，关键验收逐项 pass/fail 并引用证据。
失败、超时、缺证据、未评分都不算语义通过；不能靠关键词或文件存在判定方法有效。

同时审查评分标准：错误答案是否也能通过、还有什么关键结果没测到。
标准修改后新建实验版本，不追改原评分来制造提升。留出未向方法优化者展示的案例，
单独报告其结果；非盲评分、小样本和提示过强导致的天花板效应都要说明。

一次只改可归因的一项。比较 mandatory AC、误阻断、漏检、无效返工、首次反馈、
总时长与真实 usage；重复读取命令只是审查线索，不一定浪费。字节数不等于 token，
缓存输入不是免费输入，未知价格不填零。三次重复也不是统计显著性证明。
结果持平时检验删减候选，不因一次平分删除安全规则或宣称 Skill 无效。

真实多轮交付才可检验长程收益；state_prefix 模拟恢复只能评测该局部决定，
不能证明真正崩溃恢复、调度或最终交付已通过。报告只读，不写运行 verdict。
